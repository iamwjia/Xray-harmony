# PC1 · 定路实验包（gate-0a）：`P-27` / `P-30` 可直接执行版

> 归属任务：PC1｜作者：solution-architect｜日期：2026-10-18
> 目标：让执行者在 **0.5~1 人日**内跑完四个实验，并对「拓扑走 A1 / A3 / 改方案」给出**二值可判定**结论。
> 上游依据：`design.md` §3.4（gate-0a 决策树）、§5.0（防环四机制）；`risks-and-roadmap.md` §5 中 `P-27`/`P-30` 卡；平台事实见 R2（`research/harmony-platform-constraints.md`）§3.1/§3.2/§4.3/§9.5/§9.6。
> **全局纪律**：所有判据**只看数据面或可观测信号**；「配置已写入」「API 返回成功」**一律不构成通过**。

## 0. 一页速览

| 实验 | 对应 | 要回答的问题 | 二值判定 |
|---|---|---|---|
| **A** | `P-30`·a2 | `blockedApplications=[自身包名]` 能否既挡住自身出站回环，又不掐死 tun | 通过 = 主进程出站 IP ≠ tun 出口 IP，**且** tun 计数持续非零 |
| **B** | `P-30`·a1 | 主进程能否拿到 `VpnConnection` 并让 `protect()` 真正生效（含扩展进程内对照基线） | 通过 = 被 protect 的 socket 出口 IP = 本地 IP，**且** tun 计数持续非零 |
| **C** | `P-30`·a3 | `sockopt.mark` / `sockopt.interface` 在本机是否被系统接受 | 通过 = 出站建连成功且出口 IP = 本地 IP（未被 tun 捕获） |
| **D** | `P-27` | `VpnConnection` 实例/句柄能否跨进程获得或传递 | 通过 = 主进程侧拿到可用对象/句柄并成功调用 `protect` |

**三选一（A/B/C）任一通过 ⇒ 防环成立**；再据 **D** 与 A/B 的组合定拓扑（见 §5）。**三者全不通过** ⇒ 进「改方案」分支。

## 1. 最小工程骨架

### 1.1 必须有的东西（仅此四项，不要多建）

| # | 组件 | 作用 | 备注 |
|---|---|---|---|
| 1 | **HAP**（entry 模块） | 承载 UIAbility + VpnExtensionAbility 声明 | Stage 模型；`compatibleSdkVersion` 按目标机最低档设定（建议与本项目一致：12，见 design §9.1） |
| 2 | **UIAbility** | 主进程侧：触发实验、显示计数、持有探针请求 | 实验 B/D 的关键——**主进程**是判定对象 |
| 3 | **`VpnExtensionAbility`**（`module.json5` 中 `extensionAbilities[].type="vpn"`） | 扩展进程侧：`createVpnConnection()` → `protect()` → `create(VpnConfig)`；跑 tun 读写循环 | 只需"起 tun + 读包 + 计数"，**不需要真代理** |
| 4 | **观测面板**（UI 或 hilog 二选一） | 输出 tun 收发字节、探针结果、错误码 | 建议 hilog 结构化输出（`demo.exp` tag），便于 `hdc shell hilog` 抓取与回填模板 |

> 不需要：Xray 内核、tun2socks、订阅、路由规则、加密。**本实验只验证"通路与归属"，不验证协议。**

### 1.2 关键 API 调用序列（顺序不可改）

```
UIAbility（主进程）
  └─ vpnExtension.startVpnExtensionAbility(want)      // 首次触发系统授权弹窗
       ↓（配置经 Want.parameters 单向传入：blockedApplications 名单等）
VpnExtensionAbility（扩展进程）
  ├─ vpnExtension.createVpnConnection(context)        // 得到 VpnConnection 实例
  ├─ conn.protect(tunnelSocketFd)                     // 保护隧道 socket（在 create 之前！）
  ├─ conn.create(vpnConfig)  → 返回 tun fd           // 建 tun
  └─ 循环 read(tunFd) 累加字节计数 → hilog 输出
```

**三个最容易卡住的点**（按踩坑概率排序）：
1. **签名与设备**：必须先 `hdc` 看到真机（`hdc list targets`）；调试证书 + Profile 需绑定设备 UDID；首次连接系统会弹 VPN 授权，**拒一次后续要引导用户去设置重开**（见 R2 §3.2）。
2. **`protect()` 的时序**：必须 `create(VpnConfig)` **之前**完成 protect；写反了表面能跑，实际必然成环（现象：探针全超时）。
3. **`VpnExtensionAbility` 内的禁用 Kit**：不要 import `contact`/`geolocation`/`multimedia.audio`/`camera`/`telephony.*`（R2 §3.2），否则**进程异常退出**且报错不直观。

### 1.3 各实验复用关系

| 复用部分 | A | B | C | D |
|---|---|---|---|---|
| HAP + UIAbility + 扩展 Ability 起 tun | ✅ | ✅ | ✅ | ✅ |
| tun 收发计数 | ✅ | ✅ | ✅ | — |
| 出口 IP 探针 | ✅ | ✅ | ✅ | — |
| 主进程访问 `VpnConnection` | — | ✅ | — | ✅（同一段代码，判定不同） |
| `sockopt` 出站配置 | — | — | ✅（需一个能建出站 TCP 的最小内核或原生 socket，见 §4.3） | — |

> **建议执行顺序：D → A → B → C**。理由：D 最便宜（0.2~0.4 人日）且决定 A3 是否有调用入口；A 次之（只改配置）；B 依赖 D 的结论；C 需额外造出站。

## 2. 观测基座（四个实验共用，先建好再跑）

### 2.1 三个观测手段

| 手段 | 怎么取 | 用途 | 注意 |
|---|---|---|---|
| **O1 tun 字节计数** | 扩展进程 `read(tunFd)` 的累计字节，hilog 每秒打印一次 | 判断"tun 是否仍在收发包" | 必须**分方向**（读/写）分别计数；只统计 read 会漏判 |
| **O2 出口 IP 探针** | 主进程向一个「只回显 client IP」的公网端点发起请求，记录返回的 IP；同时记录**节点出口 IP**（可先不接节点，用"关闭 VPN 时的本地出口 IP"作对照） | 判断"自身出站是否被捞回 tun" | **绝不能用"本机 curl 成功"当证据**——那可能只是系统恢复了直连 |
| **O3 错误码 + hilog** | `hdc shell hilog -r` 抓 `demo.exp` tag；记录异常码（如 `16000xxx`、`201`、`801`、`2203002`） | 区分"没拿到对象"与"拿到但无效" | 每次实验前清一次日志，避免串场 |

### 2.2 判定所需的基线（每个设备档位先采一次）

| 基线 | 采集方式 | 用途 |
|---|---|---|
| B1 本地公网出口 IP（未连 VPN） | O2，VPN 未启动时请求探针 | 判定"未被捞回"的参照值 |
| B2 tun 空载计数 | O1，VPN 起后 30s 不发任何业务流量 | 区分"背景噪声"与"真实流量" |
| B3 一次已知业务的计数增量 | 通过 tun 访问一个大文件 10s，记增量 | 作为"tun 正常收发"的量级参照 |

> 阈值建议（写入模板，可按机型修正）：**tun 计数正常** = 30s 内读向增量 ≥ 100 KB 且连续 3 个采样点均非零；**tun 计数归零** = 连续 30s 增量 < 1 KB。

## 3. 实验 A（`P-30`·a2）：`blockedApplications=[自身包名]`

### 3.1 要回答
排除自身包名后，**自身主进程出站是否不再被自己的 tun 捕获**，同时 **tun 是否仍在正常工作**。

### 3.2 步骤
1. 配 `VpnConfig.blockedApplications = [本应用包名]`（`trustedApplications` 留空，二者互斥，见 R2 §3.1）。
2. 起 VPN，等 `Connected`（扩展进程 `onCreate` 完成 + tun fd 非负）。
3. **同时**做两件事：
   - 主进程每隔 5s 请求 O2 探针一次，记录返回 IP（共 6 次）；
   - 另一台设备（或本机浏览器经 tun）持续产生业务流量，让 O1 的读向计数有真实增量。
4. 采 60s，记录 O1 每秒增量与 O2 每次返回的 IP。

### 3.3 观测与判定（二值）

| 观测 | 通过条件 | 失败形态 A1「没生效」 | 失败形态 A2「过头」 |
|---|---|---|---|
| O2 与 B1 对比 | 探针返回 IP **== B1（本地出口）** ⇒ 未被捞回 | 返回 IP ≠ B1（等于隧道出口）或无返回（超时） | — |
| O1 读向计数 | 30s 增量 ≥ 100 KB 且连续非零 | — | 逐秒恒为 0（tun 无流量） |

- **通过** = 两个方向同时满足（O2 未被捞回 **且** O1 正常收发）。
- **A1 失败（没生效）**：探针 IP 变成隧道出口 → 说明自身出站仍走 tun（可能成环）→ 转实验 B。
- **A2 失败（过头）**：tun 计数恒 0 → 说明整包排除把扩展进程一起排掉了 → **a2 不可用**，转实验 B。

> ⚠️ 判别要点：两种失败**表现相反**，但都属"a2 不可用"，不要只测一个方向就下结论。**只看配置是否写入等于没测。**

## 4. 实验 B（`P-30`·a1）：`protect()` 的可用性与作用范围

### 4.1 要回答
① 扩展进程内 `protect()` 是否真的有效（**对照基线**）；② 主进程能否拿到对象并让 `protect()` 生效。

### 4.2 步骤（两段，先基线后主进程）
1. **B-0 基线（必做）**：在扩展进程内创建一条出站 socket（连 O2 探针）→ `protect(fd)` → 请求探针 → 记录返回 IP。
   - 预期：返回 IP == B1（未被 tun 捕获）。若连这一步都不成立，说明**protect 本身不可用**，直接跳 §5 的「改方案」分支。
2. **B-1 主进程获取对象**：主进程尝试 `vpnExtension.createVpnConnection(context)`（用主进程上下文）。
   - 记录：返回值是否为对象 / 抛出的错误码。
3. **B-2 主进程 protect**：若 B-1 拿到对象，主进程建 socket → `protect(fd)` → 请求探针 → 记录 IP。
4. 全过程中同时看 O1（确认 tun 仍正常）。

### 4.3 观测与判定

| 现象 | 判读 |
|---|---|
| B-0 探针 IP == B1 且 tun 正常 | protect 在扩展进程内有效（预期成立）→ A1 的防环基座可用 |
| B-1 抛错 / 返回 undefined / 提示上下文不匹配 | **"拿不到对象"** → a1 不可用，转实验 D（看能否 IPC 传递） |
| B-1 拿到对象，B-2 探针 IP ≠ B1（或超时） | **"拿到但无效"** → a1 不可用（对象跨进程后行为退化），转实验 D |
| B-2 探针 IP == B1 且 tun 正常 | **a1 可用** |

> **"拿不到"与"拿到但无效"的区分方法**：看 B-1 的返回值/异常（调用入口是否存在）与 B-2 的探针 IP（行为是否生效）。**两者都不看代码成功与否，只看对象可得性与数据面归属。**

## 5. 实验 C（`P-30`·a3）：`sockopt.mark` / `sockopt.interface`

### 5.1 要回答
本机是否允许对出站 socket 打 `SO_MARK` / 绑定指定网卡。

### 5.2 最小验证方法（两条路，先做便宜的）
1. **原生 socket 直测（推荐，< 1 小时）**：在扩展进程内创建一个 TCP socket，依次尝试：
   - `setsockopt(SOL_SOCKET, SO_MARK, N)`；
   - 绑定接口（`SO_BINDTODEVICE` 或其等价手段）；
   - 记录 `errno`（`EPERM` / `ENOPROTOOPT` / `EINVAL` / 成功）。
2. **内核配置侧验证（若已有最小内核）**：在某出站配 `"sockopt": {"mark": N}` 或 `"interface": "wlan0"`，看内核是否**启动成功**且出站建连成功。

### 5.3 观测与判定（二值）

| 观测 | 通过 | 失败 |
|---|---|---|
| `setsockopt` 返回值 | 返回 0 | 任意非 0（记录 errno 与数值） |
| 若走上层配置：出站建连 | 建连成功且探针 IP == B1（未被 tun 捕获） | 启动失败 / 建连失败 / 探针 IP 变隧道出口 |

> **注意**：`setsockopt` 返回 0 但探针仍被 tun 捞回 ⇒ 视为**不通过**（系统接受了参数但没生效）。这条是"配置成功 ≠ 生效"的典型陷阱。

## 6. 实验 D（`P-27`）：`VpnConnection` 实例/句柄能否跨进程

### 6.1 要回答
主进程能否**获得**该实例或等价句柄（这是 A3 的调用入口前提）。

### 6.2 步骤（三条路径依次尝试，任一成功即通过）
1. **直接获取**：主进程用自身上下文调 `createVpnConnection`（同实验 B-1，可复用）。
2. **IPC 传递**：扩展进程把实例/句柄作为参数经 IPC 传主进程（如 RPC/序列化通道）。
   - 观察：是否抛"不可序列化"/"跨进程类型不支持"等错误；若传递成功，主进程调用一次 `protect` 看是否生效。
3. **共享标识**：若实例不可传，尝试传 `vpnId`（API 20+ 的多 VPN 标识）或文件描述符类句柄，看主进程能否据此构造出可调用的对象。

### 6.3 判定

| 结果 | 判读 |
|---|---|
| 路径 1 成功且 `protect` 生效（同 B-2） | **D 通过（a1 可用）** |
| 路径 2/3 成功且 `protect` 生效 | **D 通过（a1 经 IPC 可用）** |
| 三条路径均拿不到可用对象 | **D 不通过** → a1 不可用 |

## 7. 结论映射表（二值，四选一 → 拓扑）

> 记 `A`/`B`/`C` 为对应实验通过与否，`D` 为实例/句柄可达与否。
> **"防环成立" = A 或 B 或 C 任一通过。**（B 通过即含 D 通过）

| # | A(a2) | B+D(a1) | C(a3) | 防环 | **拓扑结论** | 附加处置 |
|---|---|---|---|---|---|---|
| 1 | ✅ | ✅ | 任意 | 成立 | **A3 可行**（先验默认形态），a2 作建连期加固 | 建议同时启用 a2 + a1：a2 覆盖建连期，a1 覆盖运行期 |
| 2 | ✅ | ❌ | 任意 | 成立 | **A3 可行**（仅靠 a2） | a1 不可用 → 运行期无二次防线，`D-32` 健康判定必须覆盖"出站被捞回" |
| 3 | ❌ | ✅ | 任意 | 成立 | **A3 可行**（仅靠 a1） | 无建连期排除 → 首包窗口需靠 `protect` 及时完成（统一工厂封装，见 design §5.0） |
| 4 | ❌ | ❌ | ✅ | 成立（但脆弱） | **建议走 A1**：仅靠 mark/interface 防环依赖系统策略路由，A3 下无进程级兜底 | 若坚持 A3，必须在方案里写明"依赖 mark/interface 生效"这一前提 |
| 5 | ❌ | ❌ | ❌ | **不成立** | **A1 强制**（内核驻扩展进程，同进程 `protect`） | **前提：B-0 ✅**（扩展进程内 protect 有效）；B-0 ❌ 时见第 6 行 |
| **6** | 任意 | 任意 | 任意 | **B-0 ❌** | **改方案**（A1 / A3 均不成立） | **平台级否决**：不是"换拓扑"能解决。走 §8 末行，上报 Leader 裁决；本行优先于第 1~5 行 |

**判定纪律**：不允许出现"部分可用""基本可用"。每个格子只能是 ✅/❌；若出现"时好时坏"，按**❌**记并在备注写复现率（≥3 次中几次失败）。

> **术语对齐（Z1/PC5 核对，2026-10-18）**：第 6 行「平台级否决」是本文的通俗说法；**门禁语义以 `risks-and-roadmap.md` §8 为唯一权威**——对应口径是 §8.1 `B-02` 红灯「**无路可退**」（`P-27`/`P-30` 均属 `B-02` 成员）+ §0「`B-02`/`J-01` 不通过 ⇒ 产品在当前平台上不成立，**不是降级交付**」。两处措辞不一致时，**以 K1 §8 为准**，本文不改 K1；汇报时请引用 K1 原句，避免同一事实被读成两种处置。

## 8. 失败分支处置（每个实验失败后做什么）

| 失败项 | 下一步 | 设计侧改动 |
|---|---|---|
| A 失败（两种形态都算） | 转 B → C → D | 第 5 章 §5.0 防环机制表：a2 行标「不可用」并写明失败形态 |
| B-0 基线失败（扩展进程内 protect 无效） | **直接跳此表末行「改方案」** | A1 的防环基座塌陷，第 3 章拓扑三态需重写 |
| B 失败、D 失败 | 转 C | §3.4 gate-0a 中 a1 分支标「不允许」，A3 若无 a2/a3 支撑即出局 |
| C 失败 | 若 A 亦失败 ⇒ 改方案 | 第 5 章删去 mark/interface 路径，标注"本平台不可用" |
| D 失败 | 拓扑按 §7 表 2/3/4/5 行判定 | 若 A 通过：A3 仍可行（a2 不依赖对象）；若 A 也失败：A1 |
| **改方案（A/B/C 全失败且 B-0 失败）** | 上报 Leader + K1 | 备选：①由 tun2socks 统一承接出站、内核只做协议 ②限制路由捕获范围（放弃全局代理语义）。**属产品形态变更，须 Leader 裁决** |
