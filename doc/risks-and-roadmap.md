## 0. 给决策者的一段话

> **`B-02` / `J-01` 不通过 ⇒ 产品在当前平台上不成立，不是「降级交付」。**
> xray-harmony 的可行性押在**一个**技术假设上：**Xray-core 能否以 so 同进程加载并跑通 tun 数据面**。其余需求、设计与排期全部建立在它之上。

**为什么没有兜底**
1. 手机端三方应用**无法创建任何独立子进程**（`16000061` / `801` / `NCP_ERR_NOT_SUPPORTED`），「内核独立进程 + gRPC」路线在本平台不存在；
2. 形态 B（本地代理端口）已由范围决策排入 **V1**，MVP 内无替代形态；
3. 因此形态 A 失败 ⇒ 产品无形态可交付，只能「暂停商业化」或「收缩为 ArkWeb 容器内转发（仅浏览器场景，需产品重新定位）」——两者商业价值与形态 A 不在同一量级，**不是同一产品的降级版**。

**最早知道答案的成本（分形态）**

| 决策形态 | 判定路径 | 最短周期 | 由什么决定 |
|---|---|---|---|
| **自用 / 内测** | PoC 链（不给客户看） | **基线 4~5 周，含缓冲 5~6.5 周** | **内核编译可行性与数据面验证**（不由审批决定） |
| **公开发行** | 上述 PoC + 资质链 | PoC 周期 **＋** 许可周期 | **IP-VPN 类《增值电信业务经营许可证》**（法定审查 60 日内；社区实际 20~40 个工作日【社区观测值】）+ 企业主体与注册资本门槛 |

> 结论：**「最短工期由内核编译可行性与分发策略决定，不由审批决定」**。仅当选择公开发行时，许可周期才进入关键路径，且应尽早立项（与开发并行）。
> 推论：**投入不到 4~6.5 周即可判定技术可行性 ⇒ 正确顺序是「先证伪、再补全设计」，不是「先完成设计再验证」。**

**竞争态势的判断**：参考实现证明了「技术可行」，但**没有证明「产品可用」**（只发源码、单人维护、不内置订阅/规则、主动放弃大众用户）⇒ **我们的空间在「产品完整度」，不在技术首创**。

## 2. 方法论纪律（本文全部结论受其约束）

1. **无证据不结论**：每条平台事实标注依据类型——`官方原文` / `官方问答口径` / `单实现实证` / `社区观测值` / `推论` / `未验证`。推论不得当作事实使用。
2. **已知答案为否的项不进架构门禁**。留一个已知为否的项在门禁里，等于**制造假门禁**——红灯时会误导处置方向（据此 `P-06` 已出闸，仅作回归确认）。
3. **「未观测到上限」≠「无上限」**。全档通过时只能写「未观测到上限（观测上限 N）」。
4. **两个高危反推**：「从实现反推设计意图」（例：数组顺序）与「从文档反推行为」（例：文档说"不能同时配置"≠ 知道"同时配置会怎样"）。两者都必须标为推论。
5. **假设少 ≠ 风险低**。工程量与失败概率是两把尺子，不可合成一句"哪个更好"。
6. **真机结论优先**：模拟器（x86_64）在 ABI、`BEARER_VPN` 状态、分身/多用户、长时任务冻结策略上与真机不同，相关项**仅真机**。

## 3. 关键路径与里程碑

### 3.1 里程碑

| 里程碑 | 目标 | 交付物 | Enter Criteria | Exit Criteria（门禁） |
|---|---|---|---|---|
| **M0 内核可运行性** | 证明 Xray-core 能在 OHOS 上以 so 加载并被调用 | 可复现 so 产物 + ArkTS 成功调用 + 回调压测报告 | 具备真机与 OHOS NDK 环境 | `P-02`/`P-03`/`P-04` 三条全绿（B-01 串行链） |
| **M1 数据面可行性** | 证明 tun 数据面能跑通真实代理请求 | tun 链报告 + 数据面报告 + **`J-01` 联调记录** | M0 绿 | `P-01`/`P-20`/`P-22` 绿 + **`J-01` 通过（唯一不可跳过）** |
| **M2 分发策略决策** | 确定交付形态与资质路径 | 分发决策记录（自用/内测/公开发行） | M0 结论产出 | 用户拍板（决策点 #1）；若公开发行 ⇒ 许可立项 |
| **M3 稳定性与合规收口** | 达到可发版质量 | 崩溃观测/自恢复报告 + 合规清单 + `RG-01/02` 结论 | M1 绿 | `P-05` 绿（B-03 唯一门禁）+ `RG-01`/`RG-02` 通过 |
| **M4 V1 能力** | 形态 B 等 V1 项 | V1 验收 | M3 绿 | `P-16` 等 V1 项结论 |

### 3.2 `G0` 决策闸（二维）

- **M0/M1 红灯** → 改**内核集成路径**（换内核 / 自研 tun 实现 / 收缩为 ArkWeb 转发），**不是范围降价**；
- **M0/M1 绿 + 选公开发行** → 许可办理与开发**并行启动**，许可不阻塞技术工作；
- **M0/M1 绿 + 选自用/内测** → 直接进入 M3。

### 3.3 拓扑选型（三态，条件结论）

**本质不是「哪个更稳」，而是「把命脉押在哪个组件上」**：A3 押「主进程 Xray 不崩」（有先例、已验证能跑）；A1 押「gvisor 足够稳」（新引入、未验证）。

| 状态 | 触发条件 | 结论 |
|---|---|---|
| **当前** | `P-20` 无实测数据 | **A3 = 先验默认**（风险最低；这是风险选择，不是能力判断） |
| 升级 | `P-20` 证 gvisor 稳定 **且** `P-22`/`P-24` 通过 | A1 升级为默认（内核崩不杀 UI，体验更优） |
| 排除 | `P-20` 显示 gvisor 不稳定（崩溃 / `log.Fatal` 频发） | **A1 永久排除**（把不稳定组件与被依赖内核放同进程是最差组合） |

**A1 四项前置**：`P-20` + `P-22` + `P-24` + `P-25`。
**代价对称性**：A1 的收益是"内核崩不杀 UI"，代价是"tun2socks 崩连带杀内核 + 孤儿隧道风险 + 禁用 Kit 杀伤面覆盖内核"；A3 的收益是"弱耦合，tun2socks 崩只需重建隧道"，代价是"内核崩即应用死 + 需跨进程 loopback"。

## 6. 真机 PoC 执行前置（全项通用）

- **前置 P1｜先证明跑的是新代码**：`hvigorw --no-daemon clean assembleHap` → 安装后 `hdc shell aa force-stop <bundle>` → **冷启动**。只做 clean 不做 force-stop，会跑到旧进程旧配置 ⇒ 制造「改了没生效、日志还正常」的假象。
- **前置 P2｜先证明判据本身对**：`/proc/net/*route` **不能**用来判断 VPN 是否接管（VPN 路由在**独立策略路由表**，主表看不到属正常；v4 的 `0.0.0.0/0` 同样不在主表却能走代理）。正解：分协议打 `api-ipv4.ip.sb/ip` 与 `api-ipv6.ip.sb/ip`，**只比归属**（本地运营商=泄漏，机房=走代理），不比地址字符串（双栈站 Happy Eyeballs 优先 v6，看首页必误判）。
- **前置 P3｜设备档位是必填字段**：凡"某 API 版本起"的能力（64/256 上限=API 23、`taskKeeping`=21、`generateVpnId`=20、`onAuthorizationResult`=26、`protectProcessNet`=22），**必须指定新档位设备**。测试机常为老机型 ⇒ 不是漏测，是**从来测不到**。状态三分：`待执行` / `阻塞：缺设备` / `已完成`，不得混同。
- **前置 P4｜`VpnConfig` 变更的验收措辞**：重建触发 = **任何导致 `VpnConfig` 变更的操作**（改分应用名单 / 全局↔分应用切换 / `bypass` 翻转），Given-When-Then：`Given 用户执行任一 VpnConfig 变更 When 保存 Then 提示"将重新连接"并在重建后自动恢复`。

| 编号 | 风险 | 触发条件 | 影响面 | 可观测信号 | 缓解/兜底 | 阶段 |
|---|---|---|---|---|---|---|
| R-04 | **内核只能同进程加载**（无子进程）⇒ 内核崩溃 = 宿主崩溃 | 任意崩溃 | 可用性 | 崩溃日志/ANR | 稳定性靠「减少崩溃 + 可观测 + 快速自恢复」；`P-05`/`P-15` 并列必过 | M0~M3 |

### 8.2 联合门禁 `J-01`（唯一不可跳过）

**基准定义（与 `requirements.md §3.1` 一致，以此为准）**：

> `J-01` = 「Xray 内核以 **so 同进程加载**（`P-02`→`P-03`→`P-04`）+ **经 tun2socks 路径**跑通 tun 数据面（`P-01` × `P-20`）+ **v6 最小数据面用例**」

**`J-01` 不通过 = 产品不成立。** 它是三部分交汇，**不是单实验**（不得简写为 `J-01 = P-01`）。

判定（可观测，不接受"验证连通性"式表述）：
1. **加载段**：`P-02`→`P-03`→`P-04` 全绿（so 可复现构建、可被 NAPI 加载、异步回调不崩）；
2. **数据面段**：经 **tun2socks 路径**（`P-01` × `P-20`）用**真实 VLESS 节点**，从 ArkTS 侧发起一次 HTTPS 请求，经内核出站并**返回 HTTP 200**；
3. **统计段**：**流量统计有非零计数**（上下行均 >0）；
4. **v6 最小数据面用例**：v6 出站 + v6 DNS 各跑通一次（否则会出现「`J-01` 全绿但 v6 漏流量」的假绿灯）；
5. **恢复段**：关闭 VPN 后基础网络立即恢复（延续 `P-01` 的 ③④⑤ 判据）。

> **跨进程 loopback 不是 `J-01` 的固定项**：它是 **A3 专属**。拓扑按 `gate-0a`（`P-27`/`P-30`）结论走——A3 下须另验同应用跨进程 loopback（并入 `P-20`/`P-29`）；A1 下内核与 tun2socks 同进程，该项**不适用**（显式标 N/A，不算漏测）。

> **Z1 复检（2026-10-17）：本节缺陷已关闭。** 此前登记的「缺 v6 最小数据面用例」「未纳入 `P-20`（tun2socks）」两处缺口已由 K1 v1.2 修复——基准定义改为三段交汇（加载段 `P-02→P-03→P-04` + 数据面段 `P-01 × P-20` + v6 最小数据面用例），判定项 1~5 已分别覆盖加载/数据面/统计/v6/恢复五段；跨进程 loopback 已降为 A3 专属条件项（A1 下显式标 N/A）。**本节现与 `requirements.md` §3.1 定义一致，定义漂移 = 0。**

**与 `P-27`/`P-30` 的分工**：`P-30`/`P-27` = **定路**（哪条绕 tun 机制可用、哪条拓扑可行）；`J-01` = **跑通**。顺序写死：**先定路、再跑通**。

> 合并来源：VD-24（与 VD-25 共用脚手架；`P-27` 出"是否跨进程"结论，`P-30` 出"哪条路通"结论）。

### 9.2 可运维性与健壮性（B-03）

**`P-05` 崩溃可观测（VD-10，B-03 唯一门禁）**｜断言：abort 与 SIGSEGV 两形态下，宿主存活或可恢复，且现场可落盘。｜实验：构造两形态崩溃，记录宿主存活/重启耗时/诊断完整性。｜判定（**三条同时满足**）：①拿到**带符号栈** ②下次启动**可呈现**给用户（不得静默）③**可导出**诊断包且**不含凭据**（与 `P-08` 零明文交叉校验——诊断包是凭据泄漏最常见出口）。**只测其一形态结论无效。**｜2~3｜P0｜为否：接受整进程重启 + 诊断升 P0。

**`P-13` 冲突与拒绝路径（VD-13）**｜断言：`2203002`（已有 VPN）/`2203001`（GUEST）可检测、有可操作提示、内核状态不残留。｜实验：两 VPN 交替启动 + GUEST 场景。｜判定：三路径均捕获 → UI 明确提示 → 无残留 → **对方断开后我方仍可启动**；**判据拆两条**：①能否启动 ②启动失败时 `destroy()` 是否配对、**tun fd 是否回收**（**fd 泄漏也会表现为 2203002**，否则会把自家 bug 记成平台限制）。｜依赖：P-01。｜2｜P1｜为否：预检 + 引导跳转。

**`P-15` panic/recover（VD-15，挂 `RG-01`）**｜**事实（语言层，无需实验）**：Go `recover` 只在**同一 goroutine** 生效 ⇒ 调用边界的 recover **兜不住** goroutine 内 panic。**推论（设计）**：每个 goroutine 入口统一 `defer recover()`；边界层只作防呆。｜实验：两处各注入一次受控 panic（①cgo 调用边界内 ②goroutine 内异步回调），**结论分别记录**。｜判定：应用存活 + 状态可恢复（≤3s）+ 崩溃计数上报 + **后续请求无静默失败**；`recover` 触发次数与降级状态**在 UI/诊断包可见且可按站点名聚合**（站点名须为**封闭清单**并随版本归档）。｜2~3｜P0｜为否：不改变形态（改代码可修），但**稳定性承诺不可信** ⇒ `RG-01` 拦截。

**`P-06` 子进程能力（VD-06，已出闸）**｜断言：手机端无法创建独立子进程（**预期为否**）。｜实验：调 `childProcessManager.startChildProcess` / `OH_Ability_CreateNativeChildProcess` 观察错误码。｜判定：出现 `16000061`/`801`/`NCP_ERR_NOT_SUPPORTED` 即确认闭环。｜0.5h｜P3｜**不进架构门禁**（已知答案为否，留闸=假门禁）；若意外可用则回炉第 3 章。

### 9.3 数据面与网络（B-04）

**`P-28` SOCKS UDP（VD-20）**｜断言：Xray SOCKS 入站支持 UDP ASSOCIATE，tun2socks 的 UDP（QUIC/DNS/VoIP）可经其转发。｜实验：HTTP/3 站点 + DNS over UDP + 语音；**UDP 并发数与丢包率同时记录**。｜判定：QUIC 可用、DNS over UDP 全通、无持续回落；**支持 UDP ≠ UDP 好用**。｜依赖：P-20。｜2~3｜P1｜为否：**属功能缺陷非性能问题** ⇒ 明示能力边界 + QUIC 回落引导。

**`P-29` 同应用跨进程 loopback（VD-23）**｜断言：扩展进程 tun2socks ↔ 主进程 Xray 的 SOCKS 链路双向可达。｜实验：双向数据通 + 并发压测 + **主进程重启后重连**。｜判定：并发下无死锁/无 fd 泄漏、重启后自动恢复。｜依赖：P-20。｜2~3｜P1｜为否：A3 不成立 → 只能 A1；A1 亦不成立则停线。

**`P-21` IPv6 不泄漏（VD-18，`RG-02`）**｜断言：恒接管 + 内核 `block ::/0` 下 v6 不泄漏且不影响双栈探测。｜实验：v6-only 探测 + **tun 计数 vs 物理网卡计数** + **切换 Wi-Fi/蜂窝后重测** + Happy Eyeballs 站点耗时对照。｜判定：出口归属=节点机房（非本地运营商）。｜2~3（**须有可切换 v4/v6 的真机网络环境**）｜P0｜为否：关闭 v6 接管 + UI 明示（**须 Leader 批准弱化**）。

**`P-23` v6 路由下发（VQ-20）**｜断言：v6 默认路由可安全下发（四条件同时成立：`isIPv6Accepted` + `addresses` 含 v6 + `routes` 覆盖 v6 + 内核 v6 出站）。｜实验：与 `P-21` **同机同用例**比对 + 网络切换后重测。｜判定：四条件缺一即"未支持 IPv6"。｜1~2｜P1｜为否：回到 `P-21` 的弱化路径。

**`P-07` 保活（VD-05）**｜断言：三分支下 8h 锁屏连接存活。｜实验：①仅 VPN 无长时任务 ②`dataTransfer`+实况窗（**首次进度更新不得超过 10 分钟**）③`taskKeeping`（ACL，约 1 工作日【官方问答口径】），各 8h。｜判定：无 `continuousTaskCancel`、VPN 未断、pid 稳定。｜4 + 3×8h｜P1｜为否：L1→L2→接受降级并下调指标。**两类后果分列**：技术侧（冻结/断连，体验降级）与合规侧（保活声明被上架驳回，**存续风险**）。

**`P-08` 凭据存储（VD-09）**｜判定：全链路（临时文件/日志/崩溃 dump）**零明文**；ASSET（≤1KB/AES256-GCM+TEE）或 HUKS 承载密钥。｜3｜P1｜为否：内存注入 + 磁盘密文，登记"内存 dump 可提取凭据"。

**`P-09` FakeDNS（VD-08）**｜判定：开启下单次连接→断开→立即访问域名**不命中陈旧伪 IP**；解析无环回无泄漏（泄漏检测站 + 抓包双证）。两条路径分别记录：`127.0.0.1:53` 与 tun 网段（如 `10.0.0.1:53`）。｜2｜P1｜为否：FakeDNS 默认关闭（仅高级设置可开 + 风险提示）。

**`P-10` 双 API Level（VD-11）**｜判定：同一 so 在 **API 12（NEXT 5.0.0）** 与 **API 24（6.1.1）** 双端真机均可加载并起内核。｜2｜P2｜为否：抬高 `compatibleSdkVersion` 并在分发说明标注。

**`P-11` 规则热更新（VD-07）**｜判定：增量更新期间并发请求不受影响；**注入人为中断必须能回滚**且校验通过。｜2｜P2｜为否：资源随包内置，只随版本更新。

### 9.4 分发、隐私与 V1

**`P-25` 孤儿隧道（VD-22，B-07）**｜断言：主进程退出/被杀后是否留孤儿隧道。｜实验：**三种死亡方式分开测、结论分开记录**——①用户划掉任务卡 ②`hdc shell kill` 主进程 ③**扩展进程自身被回收**（主进程仍活）；每次交叉观察：扩展进程存活 / tun 是否消失 / 状态栏图标 / **对外出口 IP 是否变化**。｜判定：**本机 `curl` 成功不构成证据**（可能只是恢复直连，会把结论判反）。｜2~3｜P0｜为否（即存在孤儿）：看门狗（三条件与 + 文件锁可获取 + 观察窗口）；**强制断开入口必须不依赖主进程**（主进程死了也要能用）；修不掉则升 `RG` 类。

**`P-14` 内部渠道分发（VQ-14，B-05）**｜断言：企业内部分发通道允许分发 VPN/代理类应用且可装非调试设备。｜实验：走完整内部发布流程 → 装非调试真机 → 启动 VPN 扩展。｜判定：无驳回 + 可启动并取得授权。｜2~3 + 等待｜P1｜为否：MVP 只能自用/调试安装。

**`P-16` 跨应用 loopback（VD-16，V1）**｜断言：三方应用可监听 `127.0.0.1:PORT` 且**其他应用可连**。｜判定：①同应用可连 ②**另一应用可连**（关键）③50 并发不崩不泄漏。｜2｜V1 前置｜为否：形态 B 仅剩系统 Wi-Fi 手动代理（HTTP）与 ArkWeb 容器转发。
> **P-16 只能证明"能连"，不能证明"值得做"**——形态 B 的价值上限依赖「哪些 App 支持自定义代理」（竞品清单），此依赖为显式声明。

**`P-18` 应用枚举（VQ-18）**｜断言：三方应用可枚举已安装应用并读包名（及签名）。｜三档判定（**互斥，选定后其余档表述必须删除**）：①可读包名+签名 → 名+签名失效可见；②仅包名 → **只写包名失效可见**，禁止出现签名表述；③均不可读 → 「疑似失效」（点击条目探测 + 重选引导），不承诺自动检测。｜1｜P0（决定分应用选择器数据源）｜为否：分应用代理降 P1（改手动输入包名的专家功能）。

**`P-19` 状态感知（VQ-19）**｜断言：VPN 运行期被关闭/夺走时应用能感知。｜实验：五档死亡方式分列（划掉 / `kill` / 低内存回收 / 息屏后台被杀 / 崩溃）覆盖三场景（用户断开 / 其他 VPN 抢占 / 系统回收）。｜判定：即时档 ≤1s 或探测档 ≤5s（前台）/≤30s（后台）；**`BEARER_VPN` 只表示承载为 VPN，不等于隧道健康**（须另测"承载事件到了但隧道已死"）。｜1~2｜P1｜为否：UI 显示最后确认时间，不得假装实时。

**`P-26` `isBlocking` 语义边界（VQ-21）**｜断言：确定 `isBlocking=true` 进程被杀后，系统是「撤销 VPN 恢复直连」还是「保留阻断」。｜实验：五档死亡方式分列（划掉 / `kill` / 低内存回收 / 息屏后台被杀 / 崩溃），**崩溃路径可能不走 `onDestroy`，清理时机最不可控**；T0（终止时刻）以日志/`hdc` 时间戳锚定，之后每 50~100ms 探测固定外网目标，记录首个"直连成功"时间戳，两者差即泄漏窗口 W；**样本 ≥20 次，报 P50/P95/max**（安全窗口看最坏值，不看平均）。｜判定：两分支结论对应两套门禁——①「恢复直连 + 窗口数秒级」= **已知安全边界**（不是缺陷），须首发版首次连接一次性明示；②「保留阻断」= 定位亮点，但 `RG-02` 须追加「阻断是否覆盖 v6」（否则出现"v4 断、v6 通"的假 kill switch）。｜1~2｜P1｜为否（语义不可判）：文案只允许写"进程终止后的流量行为见实测"。

**`P-12` fd 跨进程传递（VD-12，条件性）**｜断言：tun fd 可跨进程传递（**仅方案 B/A2 适用**）。｜实验：扩展进程取 fd 后经 IPC 交外层进程双向读写。｜判定：双向数据通。｜**前置：决定自研 `openharmony` tun 实现时才需执行**（不是"性能不达标"才做；自研成本约 **10~15 人日** + MPL 开源义务 + 永久合并债）。｜3~4｜条件性｜为否：A2 永久关闭，锁 A1/A3。

**`P-31` 多 VPN 共存准入（VQ-23，条件性）**｜断言：`generateVpnId()`（API 20+）的多 VPN 共存准入限制与 **IPv4-only** 影响。｜实验：连续启动两个 VPN 扩展，观察第二个是否成功；开启共存后验证 v6 场景表现。｜判定：成功=可用（按多 VPN 设计），报错=按单 VPN 设计。｜**前置：MVP 决定不利用多 VPN ⇒ 本项仅"若考虑多 VPN / 后续期次"时执行，占 P 号不占预算。**｜1~2｜条件性｜为否：维持单 VPN 槽位设计（当前默认）。

**`P-17` 白名单上限（VQ-17）— 已取消**｜原因：官方文档已明确 **API 23 前 64 / API 23 起 256**，两列表互斥 ⇒ 实际可用即 64/256（不相加）。保留可选低成本回归：真机确认超限错误码；**若只做一档，优先做 API 23+ 的 257 项反向验证**（65 项是回归、257 项是新特性验收，后者更易漏）。**判定须验"第 N+1 个应用流量是否真走 VPN"**，只看 `create()` 成功会假绿。

### 9.5 代码证据支撑的关键结论（非独立 PoC，供上述卡片引用）

| 结论 | 依据 |
|---|---|
| 三种代理模式各有现成防环路径，均不需 `protect()`（`protect` 全仓库零调用） | 源码 + 作者断言（**先例，不等于平台无等价原语**） |
| 仅代理所选模式下自身天然不进 TUN | `selectedApps = appList.filter(app => app !== selfBundle)`（输入侧排除自身，**唯一可靠依据**；数组顺序无语义） |
| 名单与路由**同一次 `create()` 提交** ⇒ 改名单必重建断线 | `VpnConfig` 赋值处 + `create()` 调用点 |
| 分应用只能靠系统 VPN 列表 | 内核拿不到连接归属应用；平台不暴露应用枚举 |
