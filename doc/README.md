## 0. 最需要先知道的三件事

> 这三条是本项目的**决策前提**，不是结论细节。若只读一段，读这段。

### ① 关键路径「依分发形态而定」，不是一句话能说完的

| 形态 | 是否有资质审批前置 | 最短工期由什么决定 | 量级 |
|---|---|---|---|
| **自用 / 调试安装**（≤100 台设备） | **无** | **PoC 结论**（内核能否编译成可加载 so + 数据面能否跑通） | 基线 4~5 周，含缓冲 **5~6.5 周** |
| **内测 / 企业内部应用分发** | 无技术审批；需企业实名 + 企业内部应用分发资格 | 资质链路与 PoC 并行 | 资质约 3~8 个工作日 |
| **公开发行（AppGallery）** | **有**：IP-VPN 类《增值电信业务经营许可证》 | **审批**（法定审查 60 日内；社区实测 20~40 个工作日）+ 企业主体与注册资本门槛（省内 100 万 / 跨省 1000 万） | **月级**，且类目可上架性本身存疑 |

- tun 级代理能力本身**在系统 API 层不需要任何华为侧审批**：`VpnExtensionAbility` 对三方开放，仅需 `ohos.permission.INTERNET`（normal 级），首次启用是**用户授权弹窗**（不是资质审批）。
- **G0 决策闸** = 「PoC 技术结论 × 分发策略」二维判定；**G0 之前不锁定架构第 3 章的形态结论**。判定表见 [requirements.md](./requirements.md) §3.4。
- ⚠️ **术语纠正（本文档集已修正的早期说法）**：早期文档曾写「最短工期由审批决定，不由开发量决定」。该结论基于已推翻的前提（当时误以为 tun 能力需华为资质审批）。**现行口径**：自用/内测形态下无审批前置，工期由 PoC 决定；仅公开发行形态下许可才进入关键路径。演进留痕见 [requirements.md](./requirements.md) §12.3。

### ② 产品可行性押在 `J-01` 这**一个**技术假设上

- `J-01` = 「Xray 内核以 **so 同进程加载** + **经 tun2socks 路径**跑通 tun 数据面 + **v6 最小数据面用例**」。定义见 [requirements.md](./requirements.md) §3.1；门禁见 [risks-and-roadmap.md](./risks-and-roadmap.md) §8.2。
- **没有兜底**，原因有三：手机端三方应用**无法创建独立子进程**（`16000061`/`801`/`NCP_ERR_NOT_SUPPORTED`）；形态 B（本地代理端口）已排入 V1，MVP 内无替代形态；形态 A 失败 ⇒ 无形态可交付。
- **`J-01` 不通过 = 产品在当前平台不成立，不是「降级交付」。** 正确顺序是**先证伪、再补全设计**（不到 4~6.5 周即可判定可行性）。

### ③ 默认 `fail-closed`，但**进程终止即断连（无进程级 kill switch）**

- `fail-closed` 是顶层原则（`NFR-11`）：失败即阻断，而非失败即放行。
- 它有一个**已知违背面**：用户划掉应用卡片 → 系统撤销 VPN → 流量**恢复直连**。这是平台行为，不是实现选择，文档不掩盖（[requirements.md](./requirements.md) §2.2/§2.3）。
- 因此文案禁止写「具备 kill switch」；「进程终止后的流量行为」只允许写「见实测」（`P-26` 判据）。是否接受该产品事实已列为待用户拍板项 `U-9`。

## 3. 关键决策摘要（ADR 摘要）

> 完整论证、候选评分与被否方案见 [design.md](./design.md) §2；此处只给「选了什么 / 为什么 / 代价」。

| 决策 | 选了什么 | 核心理由 | 代价 / 前提 |
|---|---|---|---|
| **D-01 内核集成路线** | 内核以 **so 同进程加载 + NAPI** | 手机端无子进程能力，独立进程路线在本平台不存在 | Go 产物必须由 OHOS NDK 工具链产出；崩溃即宿主崩溃 |
| **D-02 排除独立子进程** | 明确排除「内核独立进程 + 本地控制接口」 | `16000061`/`801`/`NCP_ERR_NOT_SUPPORTED`（R2 §4.3） | 无隔离，稳定性只能靠「少崩 + 可观测 + 快恢复」 |
| **D-21 Go 工具链** | 锚定 **GA v26.3.27**、持有 fork，不追 HEAD | 官方 Go 无 `ohos` 目标；`GOOS=openharmony` 是唯一可行路径 | **R-01 供应链风险**：上游 beta fork 停更即无法升级内核 |
| **D-22 数据面** | **tun2socks 旁路（方案 A）**为默认 | `proxy/tun` 在 openharmony 下编译为 stub（源码级确定，非待验证） | 多一次拷贝与一个进程内组件；A2（fd 直连）需自研 tun + 承担 MPL 开源义务 |
| **D-04 进程拓扑** | **三态条件结论**：A3 先验默认，`P-20` 证明 gvisor 稳定后 A1 可升级，不稳定则 A1 永久排除 | 「把命脉押在哪个组件上」的取舍，不是「哪个更稳」 | 拓扑未定 ⇒ 第 3 章为条件结论，`gate-0a` 未定前不锁形态 |
| **D-25 IPv6** | **恒接管 + 内核 `block ::/0`** | `isIPv6Accepted` 默认 false ⇒ 默认直漏；fail-closed 要求阻断 | 访问 IPv6-only 站点需用户显式开启；`RG-02` 发版门禁 |
| **D-28 分应用分流** | 自建预置包名表 + 手输 + 失效提示，双档上限 64/256 | 三方无法枚举已安装应用、无法按进程粒度、名单按包名逐个 | 包名变更/分身会静默失效，须提供失效可见 |
| **D-32 健康判定** | **唯一实现**（一阶 fd 写 + 二阶心跳），含故障注入 | 避免「多处各自判断」导致 UI 状态说谎（红线 1/3） | 需 `P-19`/`P-26` 语义确定后才能定文案 |
| **D-16 安全存储** | ASSET（≤1KB 凭据）+ HUKS（密钥）+ RDB 加密库 | 全链路零明文（`P-08` 判据） | 「内存 dump 可提取凭据」须显式登记 |
| **D-19 分发路径** | 三路径 P-a 自用 / P-b 内部分发 / P-c 公开放行，含「审核不通过时走哪条」 | 技术成立 ≠ 商业化成立 | 公开上架依赖许可与类目判定（政策不确定项） |
| **D-09 配置模型** | 三层分离（L-A 用户域 / L-B 生成物 / L-C 运行时），**内核 JSON 绝不作可编辑真源** | 迁移可控、UI 可表达 | 与「整份 JSON 原地编辑」冲突，已裁决改为三层能力（`FR-38`） |

**被否方案（保留线索，便于日后重提时先看反证）**：纯 ArkTS 重写协议栈、Go 可执行文件 + 进程间通信、A2 fd 直连（永久关闭，除非自研 tun 成立）、`protect()` 之外的单一防环手段（三者不是同一件事，见 [design.md](./design.md) §5.0）。

## 4. MVP 范围摘要

**MVP 唯一目标**：验证 `J-01` 并交付可用最小客户端。

**MVP 闭环判定（缺一即不闭环）**
```
安装 → 首次授权引导 → 导入订阅 → 选节点 → 建立隧道 → 应用可见"已保护程度"
  → 断开/被杀 → 重开 → 一键恢复 → 诊断可导出
```

**范围内（`FR` 编号见 [requirements.md](./requirements.md) §4.2）**

| 组 | 内容 |
|---|---|
| 配置与节点 | 分享链接导入、订阅导入（含 Base64）、节点 CRUD、手动新建与校验、配置生成与合法性校验（`FR-01…05`） |
| 转发与分流 | 三态分流模式、DNS 策略（默认隧道内解析）、快速重启式节点切换（`FR-06/08/09`；`FR-07` 自定义规则编辑属 V1） |
| 连接与平台协作 | 建立连接与首次授权引导、长时任务保活、VPN 冲突诊断（`2203002`）、网络切换自动重连（`FR-10/11/12/18`） |
| 三条红线 | UI 状态不说谎（`FR-13`）／终止可感知（`FR-14`）／已连接但不通可检出（`FR-15`），**各自独立验收，禁止「任一通过即可」** |
| 诚实披露与恢复 | 一键恢复、首次连接一次性明示（`FR-16/17`） |
| 网络与 IPv6 | IPv6 纳入隧道（四条件）、保护状态可见（`FR-19/20`） |
| 分应用与接管面 | 分应用分流（免权限配置模式）、预置包名表、接管面变更断连告知（`FR-21/30/39`） |
| 可诊断与合规 | 连接诊断、日志脱敏导出、崩溃诊断、许可与来源声明、协议能力声明（`FR-22/23/24/29/31`） |
| 安全与自愈 | 本地入站端口安全（回环 + 可选鉴权）、数据面健康探测与自愈（`FR-35/36`） |

**明确不在 MVP**：形态 B 局部代理（V1）、自定义路由规则编辑（V1）、流量统计（V1）、订阅定时更新（V1）、桌面卡片启动（V1）、多语言与无障碍（V1）、规则命中可解释（V1）、高级字段三层能力（V1，已由 `FR-38` 重新定义）。

**后续期次的启动前置（不承诺）**：开机自启（需系统级合作，否则永久不启动）、多 VPN 共存（API ≥20 且确有需求，仅 IPv4）、远程更新预置应用表（需签名 + 防回滚 + fail-closed 评审通过）、`taskKeeping` 高优保活（需 ACL 白名单获批）。

**MVP 切分的关键依据**：形态 A 是唯一形态（B 不验证内核链路）；不做开机自启（平台不支持）；节点切换走快速重启（控制面无 reload 原语）；性能指标全部留待实测回填（官方与调研均禁止引用未测量级）；分应用走免权限配置（无法枚举已安装应用）。

## 6. 本次未覆盖 / 未验证的边界

> 原则：**不把缺口写成模糊表述**。下面每一条都明确「缺什么、为什么缺、怎么补」。

### 6.1 完全没有覆盖的部分

- **没有一行实现代码**。本项目交付范围是需求、设计、风险与计划，**不含工程落地**（PoC 脚本也未编写）。
- **没有真机实测数据**。所有性能/功耗/内存/吞吐指标均为「待回填」，`P-01~P-31` 全部**未执行**；本套文档中出现的每个数字要么是**工期人日估算**（唯一权威源：[risks-and-roadmap.md](./risks-and-roadmap.md) §4），要么是**法律/资质时限**（官方口径或社区观测值，已标注）。
- **没有 AGC 书面答复**。代理类应用的类目判定与可上架性未确认，属未收口项。

### 6.2 有结论但证据强度不足（结论可用，但不可当事实引用）

- `tun 零审批`：依据是「官方文档未设申请/审批环节 + 依赖 normal 级权限」的**推论**，不是官方否定性声明。
- IPv6 `::/0` 三字段写法：**单一实现来源**（含对照实验与真机验证），**未在我方机型验证**；`/proc` 路由表不能作判据（VPN 路由在独立策略路由表）。
- 防环三模式「均不需 `protect()`」：源码 + 作者断言（**先例**，不等于平台无等价原语）。
- 许可周期与注册资本：社区观测值 + 法规口径，条款号待法务复核。
- 竞品功能基线：来自公开仓库与 issue 讨论，版本可能已漂移，未做逐版本核对。

### 6.3 结构性边界（不是缺口，是设计选择）

- **形态 B 不构成形态 A 的兜底**：B 已排 V1，MVP 内无替代形态；A 失败只能暂停商业化或收缩为 ArkWeb 容器转发（需产品重新定位）。
- **进程隔离只有两层的一半**：主进程 ↔ 扩展进程有隔离；**扩展进程内「内核 ↔ tun2socks」无隔离**，一方崩溃带走整个扩展进程。
- **`isBlocking` 的停止后残留语义官方未定义**：文案只允许写「见实测」，不得写「具备 kill switch」。
- **合规边界**：`Xray-core` 为 **MPL-2.0（文件级 copyleft）**；参考实现本体为 **GPL-3.0（传染）**，代码不可抄（含 `.ets`），思路可借鉴，须登记「参考范围」。`sing-box`（GPL-3.0-or-later）不采用。

### 6.4 术语与文风边界

- 正文允许用简称「引擎层」指代**核心引擎层**（[design.md](./design.md) §1.2 定义的正式名称为「核心引擎层」）；四层正式名称只此一套：`UI 层 / 应用服务层 / 核心引擎层 / 平台适配层`。
- `【待验证】` 为规范写法；`【待真机验证】` 是其**子类**（更明确指向真机验证），二者等价看待，不要求统一（为统一格式去改他人证据文档，是拿一致性换准确性）。

## 8. 编号规则与机检基线（读文档前请先看这一节）

| 编号 | 含义 | 归属文档 | 规则 |

| `P-NN` | 验证实验（PoC） | risks-and-roadmap.md | **冻结锚点**：只增不改、不重排、不复用；取消标「已取消」留位；**与 `VD` 不同号** |

**三层语义（最容易被误读的一条）**：`FR/NFR` 是需求、`D-NN` 是决策、`VQ/VD` 是**待验证断言**——`V` 只在「存在未证实的技术或政策假设」时出现，**不是每条需求/决策都配一个**。因此「FR 无 VQ」「D 无 VD」**均属正常，不构成脱链**。

**编号规则变更留痕**：编号体系在 2026-10-17 当天经历多轮修订（曾出现「P 与 VD 同号」「`P-Q` 分区段」「编号即优先级」等版本，均已废弃）。**现行生效版本为 `team-workspace/team-conventions.md` v1.4**：`P` 独立自增、编号为冻结锚点、执行顺序与优先级由批次 `B-NN` + 追溯表「执行序」列表达。早期表述若在本套文档中出现，以规范文件为准。

4. **证据分级**写进正文：`官方原文` / `官方问答口径` / `单实现实证` / `社区观测值` / `推论` / `未验证`。**推论不得当作事实使用**。
