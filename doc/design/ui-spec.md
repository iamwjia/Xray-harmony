## 0. 文档口径

| 标记 | 含义 | 处置 |

| **必须** | 可访问性 / 误触 / 信息丢失 / 深色崩溃。每条都能用一个条件判定 | 本批必改，不接受"以后再说" |

## 1. 现状扫描（先给数，再给方案）

> **统计基线**：下表基于 `Index.ets` **261 行**版本（2026-11-22 09:05 读取）。
> 之后 `Index.ets` 已增至 **354 行**，新增「连接前请先了解」全屏须知弹层（`noticeItem` 序号徽标 + `#99000000` 遮罩），带 **5 处新硬编码色值**（`#99000000` `#FFFFFF` `#1976D2` `#333333`）与 1 个 20×20 徽标。
> ⇒ 该新界面同样要令牌化，规范已补 **§4.10（弹层/遮罩）** 与 **§5.9**。**新写的界面必须直接引令牌，不要等"以后再统一"。**

### 1.1 硬编码规模

| 文件 | 含硬编码色值的行数 | `fontSize()` 调用数 |
|---|---:|---:|
| `pages/NodeEdit.ets` | 25 | 38 |
| `pages/Settings.ets` | 23 | 27 |
| `pages/Nodes.ets` | 18 | 18 |
| `pages/RoutingRules.ets` | 16 | 16 |
| `pages/Logs.ets` | 14 | 12 |
| `pages/Index.ets` | 13 | 12 |
| `pages/Licenses.ets` | 12 | 15 |
| `pages/DevPanel.ets` | 2 | 11 |
| `viewmodel/ConnectionViewModel.ets` | 5 | 0 |
| **合计** | **128 行** | **149 次** |

- **29 个不同色值**（`grep "#RRGGBB"` 去重），其中同义重复严重：`#999999 / #AAAAAA / #888888 / #90A4AE / #777777` 五种灰都在当"次要文字"用；`#F5F5F5 / #FAFAFA / #F0F0F0` 三种都在当"卡片底"用。
- **10 档字号**：`10 / 11 / 12 / 13 / 14 / 15 / 16 / 18 / 22 / 24`。缺 17/19/20/21/23，说明**不是阶梯，是逐处手调**。其中 10fp 与 11fp 合计出现位置最多（元信息、说明、日志正文全在这两档）。
- **间距**取值集合为 `{4, 6, 8, 10, 12, 16, 20, 24}`，其中 `6` 与 `10` 属非标（NodeEdit 的 `Row({space:6})`、Nodes 的 `Row({space:6})`、多处 `padding(10)`）。
- **圆角**取值 `{4, 6, 8, 12}`。
- **零处 `lineHeight`**：全仓未设行高，中文长段落（Licenses / Settings 说明）靠字体默认行距，密度不一致。
- **零处深色资源**：`resources/` 下只有 `base`，无 `dark`；`color.json` 仅 1 个键 `start_window_background = #FFFFFF`。

### 1.2 三条结构性问题

1. **颜色是"每处写死"而不是"引用令牌"**：深色模式无法通过加一套资源实现，必须先把 128 处改成 `$r('app.color.*')`。
2. **文字最小到 10fp**：10fp 在 360vp 宽屏上单字约 10vp 宽，是"能看见但读不快"的临界；日志正文、状态调试串、说明文字大量落在 10/11fp。
3. **触控目标未定义**：全仓无一处显式 `height(44)`；图标型/文字型点击区（`Text('↑')`、`Text('删除')`、`Button('+')` 36×36）命中区等于字形边界。

## 2. 三个已知问题的正面回答（结论先行）

### 2.1 节点列表一行 5 个点击区

**现状数值**：一行内 6 个子元素（文字列 + `↑` `↓` `选择` `编辑` `删除`），`Row({space:8})`，5 个间隙共 40vp。

- 命中区实测推算：`↑`/`↓` 为 `fontSize(14)` 的 `Text`，无 `padding`、无 `height` → 命中区 ≈ **14×16vp**；`选择`/`编辑`/`删除` 为 12fp 两字 → **24×17vp**。**全部低于 44×44vp，5/5 必须改。**
- 文字列被挤压：360vp 屏 − 页面 padding 32 − 行 padding 24 = 304vp 内容宽；减去 5 个间隙 40 + 5 个操作区约 112 → **文字列只剩约 152vp**。元信息行 `vmess · sub.example.com:44321` 在 11fp 下约需 190vp ⇒ 必然省略或压字。
- 更糟的是**命中区重叠**：整行 `Row` 有 `onClick`（选中），4 个文字按钮叠在上面。手指落在 `删除` 边缘 3vp 之外，结果是"选中了"而不是"删了"——错误方向还算安全；但落在 `编辑` 与行之间，就是"想编辑却只是选中"的静默失败。

**方案**：一行只保留 **2 个命中区**。

| 命中区 | 尺寸 | 行为 |
|---|---|---|
| 整行 | ≥ 64vp 高 × 全宽 | 选中该节点（主操作，正好是最高频动作） |
| 溢出按钮 | 44×44vp，右侧 | 打开 `Menu`：编辑 / 上移 / 下移 / 删除（删除红字） |

**为什么可以隐藏 ↑↓ 和删除/编辑**（信息密度硬约束下必须说清）：

- `↑`/`↓`：用户只在"把常用节点排到前面"时用一次，之后长期不动；一次操作藏在菜单里代价极小。而 `协议 · 地址:端口 · 分组 · 选中态` 四要素是**每次扫读都要看**的，**永不隐藏**。
- `编辑`：低频（导入后基本不改），且整行菜单零距离可达。
- `删除`：破坏性操作，放进菜单反而**降低误触**（现在它是唯一一个紧贴其他按钮的红色文字）。
- 收益：文字列从 **152vp → 218vp**（304 − 指示位 24 − 间隙 10 − 溢出 44 − 间隙 8），元信息不再截断。

### 2.2 编辑表单 18 个控件 + 键盘

**现状数值**（逐行数）：`TextInput` **13 个**、`Select` **1 个**、选项按钮组 **3 组（4+5+3 = 12 个 Button）**，合计 **18 个可交互控件**；每个 `Column({space:10})`，label `fontSize(12)` + 输入框（40vp 默认），单字段纵向 ≈ 17 + 40 + 10 = **67vp** ⇒ 总高约 **1206vp**，在 360×780 设备上约 **1.9 屏**。

问题不是"字段多"，是**无关字段也在要用户读**：选 `vless + TCP + 无` 的用户，仍然要滚过 WS 路径、WS Host、gRPC 服务名、REALITY 公钥、shortId、fingerprint、flow 共 7 个对他无效的字段。

**方案 A（必须）：按协议/传输/安全条件显隐**（不是折叠，是"不适用即不显示"）。

| 字段 | 显示条件 | 说明 |
|---|---|---|
| WS 路径 / WS Host | `transport == WS` | 非 WS 时这两个值恒为无效 |
| gRPC 服务名 | `transport == gRPC` | |
| SNI / serverName | `security ∈ {TLS, REALITY}` | REALITY 必填 |
| flow | `protocol == vless` | |
| publicKey / shortId | `security == REALITY` | REALITY 缺 pbk 必然握手失败 |
| fingerprint | `security ∈ {TLS, REALITY}` | |
| HTTP2 选项 | **从 `transports` 数组移除** | 内核已移除 HTTP 传输，`validate()` 会拦，但**让用户先选再被拒**是错误设计（见 §10 待裁决 3） |

典型节点（vless + TCP + 无安全）可见控件：**18 → 10**，纵向 **≈1206vp → ≈976vp**（−25%）。

**方案 B（必须）：把"保存"从"页面底部按钮"改成"吸底操作条"。**

| 项 | 数值 |
|---|---|
| 操作条高度 | 56vp（按钮 44 + 上下 6） |
| 操作条背景 | `bg_surface` + 顶部 1vp `border_subtle` |
| 按钮尺寸 | 全宽 × 44vp，圆角 22 |
| `Scroll` 内容底部 padding | **68vp**（= 56 + 12），保证最后一个字段不被操作条压住 |
| 输入框高度 | **44vp**（非 40），字号 14fp |
| label 与输入框间距 | 4vp；字段之间 16vp；Section 之间 24vp |

键盘规避：`Scroll` 已存在，字段高 44 + label 16 ⇒ 一个字段占 64vp；键盘占约 300vp 时仍可见 **4 个以上字段**，配合系统默认上移即可用。**不要**把 `Scroll` 换成 `List`（会让 `TextInput` 失焦回收）。已在 `$$`/`onChange` 双绑的写法保持不变——注释里那条"@Builder 传回调导致状态不更新"的坑不要引入。

**方案 C（必须）：错误就近显示。** 现状只有表单最底部一条 12fp 红字（`saveMsg`），用户点了保存后要往上找是哪个字段错。规范：

- 对应输入框下方 **0–4vp** 处显示错误文案（12fp `text_danger`），并给该输入框 **1.5vp `border_danger` 描边**；
- 底部保留一行汇总（13fp `text_danger`）用于读屏播报；
- 判定条件：「任一 `validate()` 返回非空 ⇒ 该字段必须有描边 + 文字错误」。

### 2.3 节点列表视觉重心错位

**现状**：节点名 15fp（选中时 Bold，`#1A1A1A` 级深色，对比 ≈17:1）；`选择`/`已选中` 12fp 但用 `#1976D2` 高饱和蓝 / `#2E7D32` 绿，且选中行整行铺 `#E8F5E9` 淡绿底。

视觉权重 = 字号 × 对比 × 饱和度。12fp 的高饱和色在 15fp 灰黑字旁边**必然先被看到**——用户扫读顺序变成"操作 → 内容"，与任务相反。

**方案（必须，三重编码）**：

| 编码维度 | 选中 | 未选中 |
|---|---|---|
| 位置 | 行左 3vp 宽 `accent` 竖条（通栏高 40vp，垂直居中） | 无竖条 |
| 图形 | 24vp `checkmark` 图标（`accent`） | 24vp 空心圆 1.5vp `border_strong` |
| 字重 | 节点名 15fp **w600** | 15fp **w400** |
| 底色 | `selected_row_bg`（**浅蓝** `#EAF1FE`，不是绿） | `bg_surface` |

三个理由：

1. **删掉"已选中/选择"文字**：它占 36vp 宽却不提供新信息（位置+图形已经说了），是纯噪声。
2. **绿色改蓝色**：绿色在本应用里已经是"连接成功"的语义（`status_connected`）。用绿色表示"选中"会让首页 hero 的绿和列表的绿互相稀释。**选中 = accent，成功 = success，两套语义不许混用。**
3. **灰度可辨**：竖条/图形/字重三者在去掉颜色后仍能区分 ⇒ 色盲用户可用；底色只是辅助。

**可判定条件**：「同一列表行内，`accent` 色出现次数 ≤ 1（仅选中指示）；`success` 色不得出现在节点列表」。

### 3.2 字号与行高（7 档，只许这 7 个数）

| 令牌 | size / lineHeight | 字重 | 用途 | 替换掉的现状 |
|---|---|---|---|---|
| `display` | 24 / 32 | 600 | 首页连接状态大字 | 22 |
| `title-lg` | 20 / 28 | 600 | 所有页面标题 | 18 |
| `title-md` | 16 / 24 | 600 | Section 标题（设置分组、许可章节） | 14 / 13 Medium |
| `body-lg` | 15 / 22 | 400 / 600 | 节点名、规则 pattern | 15 / 14 |
| `body` | 14 / 22 | 400 | 正文、设置项、输入框内文 | 13 / 12 |
| `body-sm` | 13 / 20 | 400 | 说明、提示、按钮文字 | 12 / 11 |
| `caption` | 12 / 16 | 400 | 元信息（协议·地址:端口）、时间戳、计数 | 11 / 10 |

**硬规则（必须）**：

- **禁止 `fontSize(10)` 与 `fontSize(11)`**。当前这两档承载了元信息、日志正文、说明文字，全部上移到 `caption`(12) 或 `body-sm`(13)。字号小于 12 的文本在 360vp 屏上属于"可读性风险"，不是审美偏好。
- **禁止出现 7 档以外的字号**；需要更强调就用字重（600）而不是加字号。
- **每一处 `fontSize` 必须显式配 `lineHeight`**（对应表里的值）。这是"零处 lineHeight"的正面修正。
- 可换行文本必须 `maxLines` + `textOverflow({overflow: TextOverflow.Ellipsis})`，禁止依赖默认裁切。

## 4. 组件规范

### 4.1 `PageHeader`（页面顶栏，8 个页面统一）

```
┌──────────────────────────────────────────────────────┐ 高 56
│ [←]     页面标题 20/28 w600              [计数|操作] │
│ 44×44    左对齐，距返回按钮 4vp          ≤2 个 44×44  │
└──────────────────────────────────────────────────────┘
```
- 返回：`44×44` 命中区，图标 20vp，**不再用 `Button('返回')` 文字按钮**（现状 12fp 文字按钮宽约 60vp、高 40vp，既占位又不达标）。
- 标题左对齐（现状 `layoutWeight(1)` 后紧跟计数，标题实际是"左对齐+两端撑开"，改成"标题固定、计数右对齐"）。
- 页面内容区左右 padding `16vp`；顶栏与首块内容间距 `12vp`。

### 4.2 `Banner`（横幅，3 变体）

| 变体 | 底色 | 文字色 | 用途 |
|---|---|---|---|
| warning | `warning_subtle` | `warning` | 配置读取异常、geo 未就绪、设置写盘失败 |
| danger | `danger_subtle` | `danger` | 凭据迁移失败 |
| info | `accent_subtle` | `accent` | 订阅结果、操作成功提示（非阻塞） |

- 尺寸：`padding 12`，圆角 8，文字 `body-sm`(13/20)，`maxLines 3`。
- **必须**：横幅出现时**不改变下方内容的纵向位置**（现状 `if` 插入会整体下推，用户正在看的内容会跳）；做法：横幅固定插在 header 与首块之间，接受下推，但**不叠加动画**，避免"连接失败时界面跳动"。
- **必须**：横幅文本包含"怎么办"，不能只有"哪里错了"（例如凭据迁移失败要带"请重新导入该节点"）。

## 7. 深色模式

### 7.1 落地方式（必须）

1. 新建 `entry/src/main/resources/dark/element/color.json`，**键集合与 `base/element/color.json` 完全一致**（否则缺键会在深色下回退到 base，出现浅色块）。
2. 页面源码中**不允许任何 hex 字面量**，全部 `$r('app.color.<token>')`。`ConnectionViewModel.colorHex: string` **必须改类型**：不能返回 hex 字符串，改成返回语义枚举 `ConnStatus { DISCONNECTED, CONNECTING, CONNECTED, ERROR }`，由页面映射到颜色资源。**这是深色模式的硬前提**——ViewModel 目前直接把 4 个 hex 塞进 UI，是唯一一处"颜色跨层传递"。
3. `start_window_background` 需在 `dark` 下给 `#0E1013`，否则启动瞬间白屏闪烁（"闪白"是最容易被用户当成 bug 的深色缺陷）。
4. 不强制 `setColorMode`，跟随系统（默认行为）；若后续要"手动选择"，再加设置项，本规格不引入。

### 7.3 哪些颜色**不能**简单反相（重点）

| 品牌/主色蓝 `#1565D8` | 反相后是橙色，语义完全变了；且 `#1565D8` 在深底上对比仅 2.1:1 | 换成**提亮版** `#6BA1FF`（同色相、提亮度），不是反相 |
| 语义色 绿/红/橙 | 直接反相会得到紫/青/蓝，全部丧失语义；高饱和原色在深底上还刺眼（眩光） | 保留色相不变，**降饱和 + 提亮度**（`#17703A → #4CCB77`） |
| 选中行淡绿 `#E8F5E9` | 反相成深绿后与 `success` 撞语义，用户会以为"节点已连接" | 选中一律改 `accent_subtle`（浅蓝），深色下 `#1B2740` |
| 阴影/elevation | 深底上阴影不可见，等于层级消失 | **全程不用阴影**：用 `bg_surface` vs `bg_surface_alt` 的亮度差 + 1vp `border_subtle` 表达层级 |
| 半透明遮罩 | 反相变白色蒙层，视觉上是"曝光过度" | 深色下加重不透明度（.45 → .65），保持黑色 |
| 系统图标颜色 | 从现在固定 `#546E7A` 继承，深底对比不足 | 图标色跟随 `text_tertiary` / `accent` 令牌，不写死 |
| 启动窗口底色 `#FFFFFF` | 反相逻辑不会覆盖 json 里的字面量，深色启动白闪 | 必须手写 `dark/element/color.json` 覆盖 |
| `#F5F5F5 / #FAFAFA / #F0F0F0` 三灰 | 深色下三者反相后几乎同色（`#0A0A0A`/`#050505`/`#0F0F0F`），层级丢失 | 归并为 `bg_canvas / bg_surface / bg_surface_alt` 三级，深色下分别给 `#0E1013 / #171A1F / #1E2228`（明度差 ≥ 5%） |

### 7.4 深色验收判据

- `dark/element/color.json` 存在，且**键集合与 base 完全相同**（用脚本比对 key 列表，不允许缺键/多键）。
- 8 个页面在深色下逐个截图：**无白底块、无浅色文字配浅底、无白闪**。
- 每个页面至少一个"深色专属"问题被修过：首页横幅、列表选中行、输入框边界、日志级别色 —— 这四处是浅色写死最容易漏的。

## 11. 明确不做（边界）

- **不引入任何图片/位图资源**，不用第三方 UI 库。图标只用 `SymbolGlyph($r('sys.symbol.*'))`；`sys.symbol` 具体名称随 SDK 版本变化，**若某个名称不存在，退化为字形字符**（`← ⋯ ⚠ ✓`），不得为此新增 media 资源。
- **不加底部 Tab 栏**。当前是"首页 + 二级页"导航，加 Tab 会与"返回"顶栏重复，且减少列表垂直空间。现状导航结构保留，只重做样式。
- **不改动任何业务逻辑、状态机、持久化**。`Nodes` 的 `cfgRev` 重渲染机制、`NodeEdit` 的 `$$` 双绑写法、`Index` 的 `bestEffortStop` 收尾逻辑一律不动——那些是踩过坑的结论（源码注释已写明），视觉改造不得引入回归。
- **不改动 `DevPanel` 的探针与脱敏逻辑**（`maskSensitive` 是安全边界，不是视觉对象）。
- **不加动画**。除按钮按下态外不引入转场/淡入；连接状态变化只改文字与颜色，避免"连接失败时界面跳动"放大焦虑。
