## 0. 阅读指引

### 0.1 五分钟版本

1. **形态**：MVP 只做**形态 A**（`VpnExtensionAbility` 接管全设备流量）；形态 B（应用内局部代理）属 V1，**不构成 A 的兜底**。
2. **数据面主线**：`系统 tun fd → tun2socks(gvisor) → loopback SOCKS → Xray 出站`。Xray 不直接吃 tun fd（在 openharmony 上 core 的 tun 入站编译为 stub，见 §2.4）。
3. **内核集成**：Xray-core 以 Go `-buildmode=c-shared` 产出 `libxray.so`，经 NAPI **同进程**加载（手机端无法创建独立子进程，见 §2.2/§3.1）。
4. **进程拓扑**：A3（内核驻主进程）为先验默认，A1（内核驻扩展进程）为条件升级——**由 `gate-0a/0b/0c` 三闸实测决定**，本文不预先拍板（§3.4）。
5. **三条不能妥协的红线**（来自 Q1，设计侧各有落点）：`UI 状态不说谎`／`终止可感知`／`已连接但实际不通可检出`（§3.7、§7）。
6. **fail-closed** 是顶层原则，且有一个**已知违背面**（进程终止 → 系统撤销 VPN → 流量直连），本文不掩盖（§7.1）。

# 1. 架构总览


> 层级命名严格按 `team-conventions.md` §6：**UI 层 / 应用服务层 / 核心引擎层 / 平台适配层**（不增删）

---

## 1.1 架构原则（先定约束，再定结构）

1. **内核不可替换性优先**：Xray-core 是产品核心资产，任何分层都必须保证「换内核不动 UI」和「换 UI 不动内核」。
2. **平台差异隔离在单层**：所有 HarmonyOS API 调用收敛到「平台适配层」，上层不得直接 `import @ohos.*`（NAPI 除外，因其是引擎装载通道）。
3. **控制面与数据面彻底分离**：数据面（tun 读写、加解密、转发）在核心引擎；控制面（启停、状态、配置）走应用服务层。UI 只能触达控制面。
4. **状态单一真源**：内核持有唯一的连接状态，UI 是纯投影，禁止双向状态。
5. **失败可降级、降级可见**：任何能力缺失都要有降级路径，且降级状态必须对用户可见（对应第 7 章矩阵）。

## 1.2 四层划分与模块职责

### UI 层（ArkUI / ArkTS，运行于 UI 进程）

| 模块 | 职责 | 明确不做 |
|---|---|---|
| M1 连接控制视图 | 连接/断开、状态展示、延迟与流量卡片 | 不构造内核配置、不碰 fd |
| M2 节点与订阅管理视图 | 节点列表、订阅增删改、导入导出、二维码 | 不解析订阅（交给应用服务层） |

| M5 引导与授权视图 | 首启授权说明、权限缺失引导、卡片/快捷入口配置 | 不直接弹系统授权（由扩展进程触发） |

### 应用服务层（ArkTS，运行于 UI 进程；纯逻辑，不含 UI）

| 模块 | 职责 | 关键约束 |
|---|---|---|
| M6 会话编排（Session Orchestrator） | 状态机、启停时序、冲突检测、重连策略 | 状态真源在内核；本层只做编排 |
| M7 配置服务 | 节点模型 → 内核配置生成、schema 版本与迁移、校验 | 迁移失败必须回滚 last-good（D-09） |
| M8 订阅服务 | 拉取、解析（多格式）、去重合并、更新策略、失败保留 | 失败不覆盖现有配置（D-10） |
| M9 凭据服务 | 凭据的加密存取（ASSET/HUKS/RDB 分层） | 明文只在构建配置瞬间存在（D-16） |
| M10 资源更新服务 | GeoIP/geosite/FakeDNS 资源的下载、校验、原子切换 | 原子切换 + 失败回滚（D-13） |

## 1.3 模块依赖关系（单向，禁止反向）

```
UI 层        M1  M2  M3  M4  M5
              ↓（只经应用服务层提供的接口）
应用服务层   M6  M7  M8  M9  M10  M11  M12  M13
              ↓（控制面调用，跨进程语义）      ↓（平台能力调用）
核心引擎层   M14 M15 M16 M17 M18 M19  ←→  M20(NAPI)
                                                  ↓
平台适配层   M21 M22 M23 M24 M25 M26 M27
```

依赖规则（可机检）：
- R1：UI 层**不得**直接 import 核心引擎层或平台适配层；
- R2：应用服务层**不得**直接 import `@ohos.net.vpnExtension`（只能经 M21）；
- R3：核心引擎层**不得** import 任何 `@ohos.*`（只能经 M20 与 C++ 侧）；
- R4：平台适配层**不得**包含业务规则（分流策略、订阅解析等）；
- R5：四层间只允许向下依赖；同层内 M6↔M7 等协作必须经接口而非直接持有实现。

> 这五条是**评审可执行的检查项**，也是第 10 章追溯的落点依据。

## 1.4 关键数据流（三条主链路）

1. **连接建立流**：M1(UI 点击) → M6(状态机 Preparing) → M7(生成配置) → M9(取凭据) → M21(起扩展/授权) → M20(NAPI 调 start) → M14(加载配置) → M17(DNS 就绪) → M16(路由装载) → M21(`protect` 后 `create`) → 回传 fd → M15(隧道就绪) → M18(统计开闸) → M6(状态 Connected) → M1(展示)
   - **硬序**：`protect()` 必须先于 `create()`（R2 C9）。
2. **流量流**：tun fd → M15(解密/转发) → M16(规则判断) → 出口 socket → M18(计数) → M11(实况窗周期刷新)
3. **订阅更新流**：M8(拉取) → 解析/去重 → M9(凭据加密入库) → M7(schema 校验与迁移) → 原子替换 last-good → （若已连接）M6 决策「热重载 vs 下次生效」

## 2.2 D-01 内核集成路线：进程内 so + NAPI

### 候选方案与评分

| 维度（权重） | ① 进程内 c-shared so + NAPI | ② 独立子进程 + 本地控制接口 | ③ 纯 ArkTS 重写 |
|---|---|---|---|
| 平台可行性（否决项） | ✅ | ❌ 手机端 `childProcessManager`→`16000061`、`startArkChildProcess`→`801`、`OH_Ability_CreateNativeChildProcess`→`NCP_ERR_NOT_SUPPORTED`（仅 PC/2in1、Tablet） | ✅ 形式上可行 |
| 协议覆盖完整性 | ✅ 复用 Xray-core 全协议族 | ✅ 同 ① | ❌ 无法在可维护成本内复刻 |
| 生态与安全修复跟进 | ✅ 跟随上游 | ✅ 同 ① | ❌ 完全自担 |
| 性能 | ✅ 无 IPC、无额外拷贝 | ❌ 多一次 IPC/loopback | ✅ 无跨语言开销 |
| 崩溃隔离 | ❌ 同进程（见风险） | ✅ 天然隔离 | ✅ |
| 调试可观测 | ❌ 日志混杂 | ✅ 独立 stdout | ✅ |

### 决策与依据
采用 ①。**依据不只是"可行"，而是"唯一"**：②被平台直接排除（有错误码证据），③因协议族规模不可行。

### 被否方案与理由
- **② 独立子进程**：不是"不优"，是**平台不存在**（R2 §4.3 三处设备行为差异 + 错误码）。留档以防后来者重提。
- **③ 纯 ArkTS 重写**：VLESS/VMess/Trojan/SS/Reality/XTLS + 多传输层 + 路由/DNS 引擎的规模远超移动端可维护边界，且放弃上游安全修复。

### 选后风险
1. **同进程崩溃耦合**：内核 panic/SIGSEGV 会带走宿主（扩展进程或主进程）。缓解：`D-15` goroutine 统一 recover + `VD-10` 崩溃可观测 + `D-08` 重启而非热修。**recover 只降低概率，不消除崩溃。**
2. **单进程单 Go runtime 硬约束**（R1 §4.3）：**一个进程只能加载一个 Go runtime** ⇒ 若 tun2socks 也用 Go 实现，必须与 Xray **合并进同一次构建**；否则只能用 C/C++/hev 实现 tun2socks。这条直接影响 `D-22` 的组件选择。
3. 冷启动与包体：`so` 体积与冷启动开销**无一手数据**，由 `P-02/P-24` 回填，本文不给数字。

## 2.3 D-21 OHOS Go 工具链（含供应链风险）

### 锚定版本：**GA v26.3.27**，不追 HEAD
双重理由（缺一不可）：
1. **稳定性**：GA 是发布版本，行为与协议支持经过验证；
2. **当前工具链下唯一可编**：GA `go.mod` 要求 **go 1.26**，现役 OHOS fork 为 **go1.26.5** → 可编；**HEAD 要求 go 1.27 → 现役 fork 编不了**。

> 顺带纠正一处易误判的说法：**`proxy/tun` 在 GA 已注册可用**（`infra/conf/xray.go:41`、`infra/conf/tun.go:18-29`）。**HEAD 真正独有的只有** `proxy/masque`、`transport/internet/xdrive`、`app/geodata`。因此「不依赖 HEAD」的理由不是"tun 不可用"，而是"不得依赖未发布特性"。

### 工具链三选一：为何只剩 `GOOS=openharmony`

| 目标 | 结果 | 证据 |
|---|---|---|
| `GOOS=android` | 可 dlopen，但**外来线程调 cgo 必 SIGSEGV** | 竞品实证 |
| `GOOS=linux` | IE-TLS 被 musl 拒绝 dlopen | 竞品实证 |
| **`GOOS=openharmony` + `-ftls-model=global-dynamic`** | 唯一可行；**不能加 `-tags netgo`** | 现役 `star4277/ohos-go v1.26.5-beta1` |

### 选后风险（写入风险表主表，非脚注）
- **供应链依赖**：现役 fork 为**个人维护、非官方、beta**。风险：停更即锁死 Xray 版本、无法跟进 Go 安全补丁。
- **缓解（措施而非"记录风险"）**：①内部持有 fork（固定 commit）；②记录**全量编译参数**（`-ftls-model`/`-tags`/`-buildmode`/`-ldflags`）与 **fork 补丁清单**；③固化 `.so` 产物并用 `readelf` 校验 `PT_TLS` 与 `R_AARCH64_TLSDESC` 重定位；④每次升级 Go 前先跑 `P-02`；⑤官方 fork 若长期封顶 go1.24.5（编不动 libXray 主线），则评估自维护成本。
- **失败后果**：被锁死在旧 Go → 安全补丁无法跟进；若 fork 停更且无人接手 → 内核停止演进，产品进入维护模式。

## 2.4 D-22 数据面：tun2socks 旁路（方案 A）与 fd 直连（方案 B）

### 先纠正一处易误判的表述
- **core 本身支持外部 fd 注入**：Linux 走 `proxy/tun/tun_fd.go`、Android 走环境变量 `xray.tun.fd`（`common/platform` 中 `TunFdKey`）。
- **是 wrapper（libXray）收缩了导出面**（未导出 `CGoSetTunFd`），**不是 core 没有这个能力**。两者必须分开写，否则会被读成「core 不支持外部 fd」，进而推出错误结论。

### R1 源码级结论：`proxy/tun` 在 openharmony 下是 stub（确定不可用，非待验证）
| 文件 | build tag | 行为 |
|---|---|---|
| `proxy/tun/tun_fd.go` | `//go:build linux` | 外部 fd 注入**仅 Linux** |
| `proxy/tun/tun_android.go` | `//go:build android` | Android 走 `xray.tun.fd` |
| `proxy/tun/tun_default.go` | 其余平台 | **stub，所有方法报 `Tun is not supported on your platform`** |

⇒ 鸿蒙上 `"protocol":"tun"` **必然启动失败**。要用必须**新增 `//go:build openharmony` 实现文件**，而新增/修改的 Xray 源文件按 **MPL-2.0 §3.1 必须公开**。

### 候选对比（含合规成本列）

| 维度 | 方案 A：tun2socks 旁路 | 方案 B：fd 直连内核（在 OHOS 需改造 core） |
|---|---|---|
| 先例 | Hey（OHOS 生产路径） | AndroidLibXrayLite `StartLoop(config, tunFd)`（Android）；**OHOS 无先例，且当前 core 直接不支持** |
| Xray-core 改动 | **零修改** | 需新增 `//go:build openharmony` tun 实现 |
| **MPL-2.0 义务** | 仅需提供上游对应版本**源码地址**（未修改则不扩展公开义务） | **必须公开被修改/新增的文件**（§3.1） |
| 长期维护 | 跟随上游，升级无感 | 与上游分叉，**每次升级都要合并** |
| 延迟/CPU | 多一跳 SOCKS | 少一跳 |
| 结构复杂度 | 中 | 高（fd 交接 + 生命周期 + 环路） |
| 结论 | **采用** | **仅在 A 实测不达标且愿意承担开源与分叉成本时启用** |

### 决策与理由（不依赖"参考实现这么做"）
采用方案 A。**最强理由不是工程省事，而是它是唯一能做到「Xray-core 零修改」的路线**：MPL 义务最轻（仅提供源码地址）、与上游分叉风险为零。方案 B 技术上有可能在延迟上更优，但代价是**持续的源码公开义务 + 每次上游升级的合并成本**。

### 措辞纪律
- **不写「方案 B 已被实践否决」**：当前可判定的是「core 在 openharmony 无 tun 实现（确定）」，不可判定的是「改造后性能是否更优（未验证）」。

### 选后风险
1. **gvisor 栈稳定性**：`isSocketFD` 需 Fstat 补丁（`required`），否则 `engine.Start()` **直接 `log.Fatal` 杀进程**（失败形态是进程死亡而非返回错误）。缓解：启动自检 + `P-20` 判据区分「起不来」与「起来后跑死」。
2. **UDP/QUIC**：SOCKS 需 UDP ASSOCIATE（`VD-20`）；源码级已确认 `socks`/`mixed` 支持 UDP（`"udp": true` → `UdpEnabled`），但真机高并发 UDP 稳定性未证。
3. **单 Go runtime 约束**：**一个进程只能加载一个 Go runtime**（R1 §4.3）⇒ 若 tun2socks 用 Go 实现，必须与 Xray **合并进同一次构建**；否则改用 C/C++（hev）或独立实现的栈。**这条决定组件选型，不是实现细节。**
4. **失败后果三档（不合并成"性能不达标"）**：
   - **完全不可用** → 数据面不成立 → 产品停线重估；
   - **仅 UDP 不通** → 功能性缺陷：能力边界明示 + QUIC 回落引导，仍可交付；
   - **仅性能不达标** → 下调带宽指标并对外披露。

## 2.5 D-33 节点切换策略（依据 R1 §4.2 能力边界）

R1 结论：内核**无「整体重载配置」能力**（全部 proto 无 reload 语义）；`HandlerService` 可增删 outbound，但**没有"改某个 outbound 的地址/凭据"的原语**，只能「删旧建新」且**已在途连接不迁移**；**DNS/FakeDNS/policy/统计清零都必须重启内核**。

### 候选
| 方案 | 机制 | 优点 | 缺点 |
|---|---|---|---|
| **① 快速重启（主路线）** | 停核 → `core.New(config)` → `Start()` | 语义干净、配置永远一致、实现简单 | 切换有中断（时延待 `P-20` 回填） |
| ② balancer 预置（进阶） | 启动时建好全部候选 outbound + `RoutingService.OverrideBalancerTarget` 切换 | 无中断、可秒切 | 启动时全建（内存与握手成本上升）、受单进程资源约束 |
| ③ gRPC 热改（删旧建新） | `RemoveOutbound`+`AddOutbound` | 不需重启 | 连接不迁移、tag 引用需自维护、DNS/policy 改动仍需重启 → **收益不足以覆盖复杂度** |

### 决策
①为主路线；②作为「未来期次」候选（需 `P-24` 证明内存可承受多 outbound 常驻）；**③不采用**——它把「部分配置可热改、部分必须重启」的混合状态引入系统，状态一致性代价高于收益。

### 选后风险
- 切换/重连期间的中断对用户可见 → 必须有明确的「切换中」状态与失败回滚（回滚到 `last-good`）。
- 重启路径若涉及重新解析 geo 资源，耗时可能显著上升 → 资源应常驻内存、避免每次重启重解析（与 `D-13` 资源管理联动）。

## 2.6 D-34 控制面暴露方式

- **优先进程内直调**：内核与调用方同进程时，控制面走函数调用/NAPI，**不开 gRPC**。
- 若确需 gRPC（仅 DEBUG 与排障）：绑定 `127.0.0.1` + 随机端口 + 一次性 token；发布构建关闭。

## 2.7 相对参考实现的改进（少而硬，只列真改进）

1. **跨进程状态通道**：配置走 `Want` 单向传，**状态与启动成败走正式 IPC + 显式超时对账**，日志只作诊断、不作控制信号。
   - 参考实现用「轮询扩展进程写的日志文件 + 10/12s 超时」判断启动成败；日志格式/缓冲/落盘时机任一变化即误判，且无法区分「还没起来」与「起来了但失败」。
2. **fail-closed 孤儿隧道看门狗**：主进程心跳丢失 + **文件锁可获取**（证明进程确实不在，而非仅未响应）+ 观察窗口内未恢复，三条件同时成立才 `destroy()` 并退出。
   - 理由：孤儿隧道属隐私级问题（用户以为已退出、实际仍在代理）。误杀代价 = 掉线（可感知可恢复），漏杀代价 = 隐私事故（不可感知、一次性伤害）——代价不对称，故 fail-closed。

> 本小节保持「宁可有 2 条真改进，不要 6 条似是而非」。

## 3.1 已排除方案（附证据）

### 排除一：内核编译为独立可执行文件，以子进程方式运行 + 本地控制接口
`childProcessManager.startChildProcess` → 手机 `16000061`；`startArkChildProcess` → `801`；`OH_Ability_CreateNativeChildProcess`/`StartNativeChildProcess` → `NCP_ERR_NOT_SUPPORTED`（仅 PC/2in1、Tablet）；子进程且不支持 UI、不依赖 Context、不能再建子进程、随父进程退出。
**⇒ 手机端三方应用无法创建任何独立子进程，也无法 fork/exec 可执行文件。** 桌面端常见的「内核独立进程 + gRPC 控制」路线在本平台不存在。原 `VD-06` 因此作废。

### 排除二：纯 ArkTS 重写协议栈
协议族规模（VLESS/VMess/Trojan/SS/Reality/XTLS + 多传输层 + 路由与 DNS 引擎）超出 ArkTS 在移动端的可实现与可维护边界，且无法复用 Xray-core 的生态与安全修复。

### 明确「未验证」而非「被否」（纪律要求，避免误杀更优路径）
- **tun fd 直接交给内核（无 tun2socks 旁路）**：Android 侧 `AndroidLibXrayLite.StartLoop(config, tunFd)` 经 env `xray.tun.fd` 存在**既有先例**；OHOS 侧未被证伪。参考实现 Hey **主动绕开**（两内核共用数据面 + 规避 gvisor 适配），**不构成否证**。
- 故此项保留为**方案 B（备选、待验证）**，不作为已排除方案。

## 3.3 数据面：双方案，默认 A

| | 方案 A（默认，OHOS 有实证） | 方案 B（备选，待验证） |
|---|---|---|
| 链路 | `tun fd → tun2socks(gvisor 默认 / hev 备选) → loopback SOCKS → Xray 出站` | `tun fd` 直接交内核（`xray.tun.fd` 类机制） |
| 先例 | Hey（OHOS 生产路径） | AndroidLibXrayLite（Android）；OHOS 未验证 |
| 优点 | 链路成熟、可复用 gvisor、内核与数据面解耦清晰 | 少一跳，时延/CPU 更低 |
| 缺点 | 多一跳 SOCKS（延迟/CPU/内存）、**gvisor 栈 QUIC/UDP 兼容性与吞吐需实测** | 需解决 fd 交接、路由环路、gvisor 适配 |
| 定位 | 主线 | **仅当 A 实测性能不达标时启动验证**（`P-12`） |

**方案 A 的硬要求**：
- gvisor 的 `isSocketFD` **必须打 Fstat 补丁**（`required`），否则 `engine.Start()` 直接 `log.Fatal` 自杀——**注意失败形态是进程死亡而非返回 error**（证据：参考实现 `scripts/build_tun2socks_ohos.sh:60-110`，required 判定 `:62-64`，失配直接退出 `:76-79`）。
- **SOCKS 必须支持 UDP ASSOCIATE**，否则 tun2socks 的 UDP 流量（QUIC/HTTP3、DNS）无处可去 → 表现为「能上网但很多应用不正常」的半可用状态（`VD-20`）。
- hev（纯 C，不需 gvisor 补丁）作为**有条件兜底**：自带 userspace 栈，UDP/DNS/连接回收行为差异须验证，**不当等价替换**。

## 3.4 进程拓扑：三态结论（不预先拍板）

### 【gate-0a】拓扑判定的第一前置：防环手段是否可行（三条任一成立即可）

> `protect()` 是 `VpnConnection` 的**实例方法**，实例由扩展进程 `createVpnConnection()` 得到；但防环还有两条**不需要该实例**的路径，故不能因实例不可达就判 A3 出局。

```
gate-0a 防环手段（任一成立即可）
 ├─ a2 blockedApplications=[自身包名]（★主路径：平台自带、无需特权、无需对象跨进程）
 │    ▸ 作用模型：排除的是「该应用的 IP 流量被路由进 tun」，**不是**「该应用不能读写 tun 设备」
 │      —— tun2socks 从 tun fd **读包**不经过路由判定；经 **loopback** 交给 Xray 的流量也从不经过 tun；
 │         真正会成环的是「Xray 出站连节点的那个 socket」（真实公网流量），排除它正是目的。
 │    ▸ 两结果式判定（**用数据面计数，不用"配置是否生效"**，两方向都可能静默）：
 │        ① 排除生效 且 **tun 接收流量正常** → a2 成立，且优于 protect（建连期即排除）
 │        ② 排除生效 但 **tun 接收流量归零** → a2 不可用，退回 a1/a3
 │    ▸ 常见误判（防实现期重犯）：不要把「路由」与「读写 fd」混为一谈，否则会误弃最优路径
 ├─ a3 sockopt.mark / sockopt.interface（次选：需系统策略路由/绑网卡权限，OHOS 未验证）
 └─ a1 VpnConnection 实例/句柄在主进程可达 → protect()（a2/a3 均不成立时升为首选）
```

**静态阅读需先确认三件事**（`P-27` 的 0a 前置）：
1. 全局模式配的是 `blockedApplications=[自身包名]` 还是 `trustedApplications`（**两种模式配法不同**，混读会得出反向结论）；
2. 是否同时开 `isIPv6Accepted` + v6 `routes`（决定 a2 对 v6 是否同样有效）；
3. 是否额外做了 `protect()`（**若二者都有，说明单靠 blockedApplications 不足** —— 最强的反证信号）。

> 当前标注：a2 = **结构性很可能成立，待真机确认**（不再写"大概率死"）。

**附带收益（写进 D-10/D-28 理由）**：排除自身包名后，**UI 主进程的网络请求（订阅拉取、GeoIP 下载）走物理网卡直连**——避免了"要用节点才能拉订阅"的自举死锁。

**必须证伪或证实的一条矛盾**：
> 若「按包名 = 排除该应用所有进程」且会导致 tun 收不到包，则参考实现用 `blockedApplications=[自身包名]` 却仍能让 tun2socks 工作无法解释；两种可能：①其配置与我们的信息不符（需回查源码）；②排除只影响路由、不影响 fd 读写（即上面的作用模型）。**在 `P-27` 出结论前，不得基于 a2 设计防环。**

| 步 | 判定 | 若为否的后果 |
|---|---|---|
| **0a** | 上述 a1/a2/a3 是否至少一条成立 | 全不成立 → **A1 强制**（同进程才能 protect） |
| **0b** | 主进程建 socket → 防环生效？与扩展进程内同款对照 | 仅扩展进程生效 → **A3 出局，A1 转正** |
| **0c** | 退 `mark`/`interface`；再不行退「限制路由捕获范围」（放弃全局代理语义） | 全不可用 → 需换数据面形态 |

> `P-27` 成本 0.5~1 人日（真机 + 最小 demo），**结论权重极高，故排在所有昂贵实验之前**。可与 `P-02`（构建链）并行，但编译链仍是地基。

### 结构性连锁（必须让读者理解为什么下面三条会突然变关键）

> 若 `P-27` 证明 `protect()` **只在扩展进程生效**，则「**内核必须驻扩展进程**」就从优选变成**硬约束**，A3 出局。
> 此时 A1 的三条代价 —— **内存上限（`VD-21`）、冷 cgo（`VD-19`）、孤儿隧道（`VD-22`）** —— **全部从「选型权衡」变成「必须跨过的门槛」**：它们不再是"选 A1 要付的代价"，而是"项目能否交付的前提"。
> 同理，`D-14`（禁用 Kit）的杀伤面覆盖内核这件事，也从"讨论题"变成"必答题"。

### 拓扑决策树（可执行，任何人拿到实测结果即可走到终点）

```
gate-0a  VpnConnection 实例/句柄能否在主进程获得（直接创建 / 经 IPC 传递）？
 ├─ 否 → A1 强制；J-01 判据须按 A1 重述（内核 + tun2socks 同进程）
 │        └→ 原选型判据全部升级为交付门槛：
 │             VD-17/P-20 gvisor 稳定性 → 交付能否成立
 │             VD-19/P-22 冷 cgo        → 交付阻断项
 │             VD-21/P-24 内存上限      → 能否装下内核
 │             VD-22/P-25 孤儿隧道      → 看门狗由"加固"变"必需"
 │             D-14 禁用 Kit            → 从讨论题变必答题
 └─ 是 → gate-0b  防环三选一（protect / sockopt.mark / sockopt.interface）至少一条可用？
          ├─ 否 → 改方案：tun2socks 承接出站 / 限制路由捕获范围（放弃全局代理语义）
          └─ 是 → gate-0c  gvisor 稳定性（P-20） + 内存上限（P-24） + 冷 cgo（P-22）
                   ├─ 全绿       → A1 升级为默认（体验更优：假设最少）
                   └─ 任一不达标 → A3 维持默认（先验风险最低）
```

> **J-01 判据随拓扑走**：若 `gate-0a` 判「A1 强制」，则 J-01 的判定须按 A1 拓扑重述——「内核与 tun2socks **同进程**跑通 tun 数据面 + v6 最小用例」，否则 K1 的 J-01 卡片会与本设计打架。

### 对比维度（七维，含出站 protect 与单点故障耦合度）

| 维度 | A1（内核 + tun2socks 均驻扩展进程） | A3（tun2socks 驻扩展、内核驻主进程） |
|---|---|---|
| **出站 socket 能否被 protect** | **是**（同进程，实例可达） | **待验证**（`P-27` 0a/0b）；为否则 A3 出局 |
| 失败影响面 | 内核崩 → 只停 VPN，**UI 存活可提示重试** | 内核崩 → **应用死**，用户看不到原因 |
| 单点故障耦合度 | **内核与 gvisor 同生共死**：gvisor 崩则内核一起死，恢复走完整冷启动 | gvisor 崩内核仍活，只需重建隧道，**恢复更快** |
| 假设数量 | 少：无跨进程 fd、无跨进程 loopback、无端口暴露 | 多：**必须验证同应用跨进程 loopback** |
| 内存上限 | **未知**，需实测（Go 堆 + gvisor 栈同进程） | 主进程内存通常更宽裕 |
| 被回收频度 | 扩展进程回收频度未知，可能高于主进程 | 主进程常驻要求更高（C3） |
| 首 cgo 风险 / 禁用 Kit 杀伤面 | **高**（C11 直接冲突；C6 杀伤面覆盖内核与数据面） | 低（cgo 首调在主进程，天然规避） |

### 三态决策（先保守、后优化）

1. **现在（先验默认）= A3**。理由：**A1 与 A3 不是"哪个更稳"，而是"把存活性押在哪个组件"**。A3 押在「Xray（OHOS 有先例、已验证能跑）+ 主进程不崩」；A1 押在「gvisor（新引入、未验证）足够稳定」。**假设少 ≠ 风险低**——A3 假设多但失败可恢复，A1 假设少但失败即应用死。
2. **若 `P-20` 证明 gvisor 稳定 且 `P-22`/`P-24` 通过 → A1 升级为默认**。此时 A1 收益：无跨进程 fd、无跨进程 loopback、无端口暴露、少一次拷贝（**假设最少**）。
3. **若 `P-20` 显示 gvisor 不稳定 → A1 永久排除**：把不稳定组件与被依赖内核放同一进程是最差组合。

> **A1 的真实代价（不淡化）**：A1 不是「更稳」，而是**把赌注从「内核崩」换成「gvisor 崩」**——换了个更小的赌注，不是消除风险。而「gvisor 在 OHOS 上足够稳定」恰恰是 `P-20` 要验的事。

### 主线未验证假设清单（越短越好，当前 7 条）
`VD-01/02/03`（构建链）、`VD-04`（VPN 全链路）、`VD-17`（gvisor tun2socks）、`VD-19`（冷 cgo）、`VD-20`（SOCKS UDP）、`VD-21`（扩展进程内存）、**`VD-23`（同应用跨进程 loopback，A3 默认路径下必须）**
> A1 成立后可去掉 loopback、fd 两项；A3 成立则必须保留 loopback。

## 3.5 与 UI 的解耦：跨进程状态通道（本决策优于参考实现）

- **配置下行**：`Want.parameters` 单向传递（沿用平台惯例）。
- **状态上行 / 启动成败**：**正式 IPC + 显式超时对账**；日志只作诊断，**不作控制信号**。
  - 参考实现用「轮询扩展进程写的日志文件 + 10/12s 超时」判断启动成败 —— 日志格式/缓冲/落盘时机任一变化即误判，且无法区分「还没起来」与「起来了但失败」。**本设计不继承该做法。**
- **控制面语义**（非实现）：`start(config)`/`stop()`/`status(subscribe)`/`stats(subscribe)`/`reload(config)`，**幂等 + 请求序号**，防重复下发。
- **状态单一真源在内核侧**；UI 是投影（§3.7 对账）。

## 3.6 禁用 Kit 杀伤面自查（A1 下杀伤面覆盖内核）

| 路径 | 是否触碰禁用 Kit | 结论 |
|---|---|---|

## 3.7 生命周期、状态与对账

### 状态两维定义（D-29）
- **系统承载态** = 自身状态机（`onCreate`/`onDestroy`，`onDestroy` 必调）+ 默认网络 bearer 含 `BEARER_VPN`（`getNetCapabilities()` 12+ / `on('netCapabilitiesChange')`，仅需 `GET_NETWORK_INFO`）。
- **隧道健康态** = 用户态探测：**一阶信号 = tun fd 写入返回值**（写失败/连续 EAGAIN 即失效，比心跳早且零成本）；**二阶 = 心跳**（写得进去但对端不回）。
- UI 展示以**隧道健康态**为准；系统承载态只用于「是否需引导用户断开其它 VPN」这类判断。两维任一异常**必须有独立文案**，不得合并为「连接异常」。

### 启动路径
应用图标前台启动 → **桌面卡片/服务卡片一键连接**（替代开机自启）→ 通知栏常驻快捷动作 → 「上次异常断开 → 启动后强提示重连」。**明确不承诺**开机自启（C8）。

### 状态机
`Idle → Preparing → RequestingAuthorization → Connecting(protect 先于 create) → Connected → Reconnecting → Stopping → Idle`
异常边：`AuthorizationDenied` / `Conflict2203002|2203001` / `Crashed` / `TunnelDead`（一阶信号触发）。

### 孤儿隧道：条件分支（不选边，交实测 `VD-22`）
- 冲突：R2 官方原文「调用方应用进程退出 → 系统停止 VPN」 vs 竞品现象「主进程死/被回收后扩展仍存活、隧道继续跑（其为此实现了跨进程停止标志）」。
- **可能调和解释**：正常退出触发系统停止；**非正常退出（kill -9/系统回收）时系统未必及时清理**。若如此，两者同真。
- **设计按「最坏情形」写（fail-closed）**：主进程心跳丢失 N 秒 → 扩展进程**自行 `destroy()` 并退出**。宁可断，不可静默续跑（孤儿隧道属**隐私级**问题：用户以为已退出，实际仍在代理）。
- 承诺边界（待 `VD-22` 定论后回写）：分支①「退出即断」；分支②「退出后 ≤N 秒内自动断开」。

### UI-内核状态对账（D-31）
主进程每次回前台 / 重启后，**先拉取真实状态再渲染，禁止沿用本地缓存**。理由：扩展进程可能仍存活而 UI 已被回收，反之亦然。

`【待验证】VD-22 主进程退出/被杀后，VPN 扩展进程与隧道是否继续存活（是否存在孤儿隧道）｜验证：**三种死亡方式分开测、结论分开记录**——①用户划掉任务卡片 ②`hdc shell kill` 主进程 ③扩展进程自身被回收（主进程仍活）；每次交叉观察「ps 扩展进程存活 / tun 是否消失 / 状态栏图标 / **对外出口 IP 是否变化、请求是否真经隧道**」｜注意：**本机 `curl` 成功不构成证据**（可能只是系统恢复直连，会把结论判反）｜归属：P-25（批次 B-07）`

**看门狗出口条件（fail-closed 分层）**：
1. 首选：主进程心跳丢失 N 秒 → 扩展侧主动 `stopVpnExtensionAbility` + 下次启动对账告知；
2. 若平台不允许扩展侧主动 stop → 扩展侧 `destroy()` 自身 VPN 连接（不依赖 stopExtensionAbility）+ UI 明示；
3. 仅当连 `destroy()` 也不可行 → 退化为「UI 明示 + 首次连接警告」（RG 级）。

## 3.8 保活：三层约束叠加

> C3（调用方进程退出即停 / 或孤儿风险）+ C4（无 vpn 长时任务类型）+ C5（一处申请覆盖全进程）

| 分支 | 类型 | 权限 | 附加义务 | 风险 |
|---|---|---|---|---|
| L1 | `dataTransfer` | `KEEP_BACKGROUND_RUNNING`(normal) | 首次进度更新 ≤10 分钟；进度通知**必须实况窗** | 语义不一致可能触发「业务类型不一致 → 挂起/终止」 |
| L2 | `taskKeeping` | `KEEP_BACKGROUND_RUNNING_SYSTEM`(restricted，ACL 约 1 工作日) | 上架审核复核用途 | 未获批退 L1 |
| L3 | 无长时任务 | — | — | 锁屏/后台大概率被停 |

- L1 的「10 分钟」义务可设计化：VPN 活跃期周期性刷新实况窗进度，承载真实数据（已连接时长/上下行），与第 6 章流量统计**共用数据源**，不为保活造伪数据。
- `VD-05` 实验三段对照（仅 VPN 无长时任务 / `dataTransfer`+实况窗 / `taskKeeping`），各 8h 锁屏。

## 3.9 崩溃恢复

- 崩溃面（分拓扑）：A1 —— 内核或 gvisor 崩 → 扩展进程死、连接断、**UI 存活可重试**；A3 —— 内核崩 → 应用死。
- 恢复：**重启而非热修**（`reload(last-good-config)` + 指数退避 + 次数上限 + 超限转用户介入）。
- 诊断落盘：分级日志 + 最近 N 条内核日志环形 + 崩溃时间戳 + 配置指纹；Native 崩溃用 `faultLogger`；**无符号崩溃栈等同不可运维**。
- `VD-10` 判定：abort + SIGSEGV 双形态，**只测其一结论无效**；通过口径 = 「宿主存活且重启 ≤3s」或「宿主必死但重启后恢复上次配置与订阅态」。
- **`VD-10`（崩了能查）与 `VD-19`/recover（尽量不崩）并列必过、不可互替。**

## 3.10 与系统 VPN 能力的协作边界

| 职责 | 归属 | 说明 |
|---|---|---|
| 起/停 VPN 会话、持 tun fd、`protect()`、`create()/destroy()` | VPN 扩展进程 | 唯一持有者；硬序 protect 先于 create；destroy 配对避免 fd 泄漏 |
| 数据面中继（tun2socks） | 扩展进程 | A1/A3 相同 |
| 协议与出站（Xray） | A1：扩展进程 / A3：主进程 | 由 §3.4 三态结论决定 |
| 配置生成与校验、订阅拉取与解析 | 主进程（应用服务层） | 禁止在扩展进程做（C6/C11） |
| 路由下发 / DNS / 分应用名单 | 平台适配层（`VpnConfig`） | `routes` ≤1024；黑白名单互斥 |
| 保活申请 | 应用服务层 | 一处申请覆盖全进程（C5） |
| 冲突检测与提示 | 应用服务层 | 统一入口 |

> 分层路由原则：**引擎层分流为主**（`routes` 全量入 tun，由 Xray routing + sniffing 决定），系统层仅排除自身流量与粗粒度场景。见第 5 章。

# 4. 配置与订阅

## 4.1 配置数据模型（三层分离，避免「一份 JSON 通吃」）

| 层 | 内容 | 归属 | 变更频率 |
|---|---|---|---|
| L-A 用户域模型 | 节点（名称/协议/地址/端口/凭据引用/传输参数/标签）、订阅源、分组、策略、DNS 偏好、分应用名单、**白名单高级字段**（`mtu`/`mux`/`fingerprint`/`sockopt` 部分/`sniffing`） | 应用服务层（M7/M8），落 RDB 加密库 | 用户操作驱动 |
| L-B 内核配置（**生成物**） | 由 L-A 经模板与规则生成的内核配置（入站/出站/路由/DNS/日志段） | 核心引擎层（M14 读取） | 每次会话启动/重载重新生成 |
| L-C 资源 | GeoIP/geosite、FakeDNS 池配置、规则集 | M10 管理，原子替换 | 定时/手动更新 |

**核心原则：L-B 永远是生成物，绝不作为可编辑真源。** 理由：若允许用户直接编辑内核配置，schema 迁移（D-09）无从下手，UI 无法表达部分配置，且配置、订阅更新、内核升级三者必然打架。
**字段分区（与 §5.1.0 联动）**：L-A 内部再分「系统层字段」（`routes`/`addresses`/`mtu`/`isIPv6Accepted`/分应用名单）与「内核层字段」（路由规则/DNS 策略等），**分区存储、分区呈现**——因为两者变更代价不同（前者重建 VPN 断连，后者可不断连）。

## 4.2 schema 版本与迁移（D-09）

- L-A 带 `schemaVersion`：相等→直接加载；旧→新→**逐版本链式迁移**（`v1→v2→v3`，不做跨版本跳跃映射）；新→旧（降级安装）→**拒绝加载并提示**，不尝试逆向迁移。
- 迁移前**强制快照**；失败→回滚快照 + 保留失败原因 + 转「安全模式」（仅直连）。
- 迁移器为**纯函数**，每段版本链有单测；便于回放与复现。

## 4.3 订阅解析与更新（D-10）

- 支持格式（能力边界以 R1/竞品清单确认，本稿只定架构）：分享链接列表 / Base64 批量 / 自有导出格式；**解析器可插拔**（新增格式不改核心）。
- 更新策略：手动刷新 + 定时刷新；**拉取成功但解析失败 → 保留 last-good**（不因服务端异常砸掉可用配置）；拉取失败 → 指数退避 + 连续失败 N 次标记「订阅过期」（不静默）；更新内容做**差异摘要**后原子替换，附更新前快照以便一键回退。
- 并发：同一订阅源同时只允许一个更新任务（幂等，防竞态写库）。

## 4.4 本地配置生成与校验

- 流程：L-A 节点 → 模板（按协议族）→ 补齐全局段 → **静态校验**（必填、端口、地址族、证书链）→ 内核启动自检（真实加载一次）。
- 校验分级：**阻断级**（缺必填/非法端口）禁止启动；**告警级**（MTU 偏小、规则重复）允许启动但提示。
- **生成物不落盘**（仅内存传递），避免明文凭据落盘；排障时经 M12 白名单脱敏后导出。
- **socks/mixed 入站是生成器的必需项**（见 §4.8），缺失即判配置非法。

## 4.5 导入导出

| 场景 | 载体 | 处理 |
|---|---|---|
| 单节点导入 | 分享链接/二维码 | 解析→校验→入库（凭据进 ASSET） |
| 批量导入 | 订阅 URL/文本 | 同 §4.3 |
| 导出 | 分享链接/订阅文本 | **二次确认**并明确「含节点凭据」；默认不含订阅 token |
| 备份迁移 | 自有加密包 | 需用户口令；换机迁移 = 重新导入（ASSET 与应用生命周期绑定） |

## 4.6 节点凭据安全存储（D-16）

- 分层：**短凭据（uuid/密码/私钥/token）→ ASSET**（单条 ≤1KB）；**批量结构数据 → RDB `encrypt=true`**；**密钥 → HUKS**；**偏好 → preferences（禁敏感）**。
- 凭据**不进入 L-B 持久化**：生成配置时才解密拼接，配置对象在隧道建立后即丢弃引用。
- ≤1KB 硬约束：超长字段不可截断，改为**引用式**（ASSET 存索引，正文在 RDB 加密库）。

## 4.7 配置真源与可变性（FR-38 × D-09 的裁决落地）

**原则不变：L-B 永远是生成物、不回写。** 但高级用户不能被逼死，故设三层能力（Leader 裁决）：

| 层级 | 能力 | 约束 |
|---|---|---|
| ① 白名单高级字段可编辑 | `mtu`/`mux`/`fingerprint`/`sockopt` 部分/`sniffing` 策略 | 进 **L-A 域模型**，是正经真源，可编辑、可迁移 |
| ② 生成结果只读查看/复制 | 最终内核 JSON（**脱敏后**） | **禁止回写**；复制经脱敏过滤器 |
| ③ 整份 JSON 仅「导入转换」 | 解析 → 映射到 L-A 域模型 | **不认识的字段必须明确列出并拒绝，不得静默丢弃**；映射失败整体拒绝，不做部分导入 |

> 第 ③ 条是硬要求：静默丢弃会让用户以为配置生效、实际未生效，属最难排查的一类问题，比直接报错严重得多。
> **实现要求**：导入转换器与生成器**共用同一份字段白名单常量**，避免两处定义漂移；系统层字段变更必须二次确认并告知「将断开连接并重建」。

## 4.8 订阅与资源更新的出口策略（D-35：自举与隐私权衡）

排除自身包名（§5.1.0 → a2）解决「要用节点才能拉订阅」的自举死锁，但引入两条副作用，须显式处理：

| 档 | 行为 | 触发条件 | 明示义务 |
|---|---|---|---|
| ① **默认直连** | UI 直接发请求（自身已被排除出 tun，天然直连） | 未连接/首启 | **首次拉订阅明示**「将通过直连获取，可能暴露域名」 |
| ② **隧道连通时经代理更新** | UI → `127.0.0.1:<socksPort>`（SOCKS5）→ Xray 出站 → 节点 | 已连接 | 无（不暴露域名） |
| ③ **内置资源兜底** | 随包内置 GeoIP/geosite 基线 | 更新失败/无网络 | 提示「规则数据可能过期」+ 重试入口 |

**② 的可行性（不需改内核、不需断连）**：loopback 不经过 tun（与 a2 同一原理）⇒「自身被排除」不构成障碍；**复用现成 socks/mixed 入站**，无需给 core 增加 HTTP 客户端能力；**无需把自身包名移出排除列表** ⇒ 不断连、不重建 VPN。因此「临时移出排除 → 重建 VPN」这条昂贵路径**不采用**。

**两种出口的隐私代价（必须都写，诚实权衡）**：

| 出口 | 暴露对象 | 边际代价 |
|---|---|---|
| 直连 | 订阅域名暴露给**本地 ISP / 网络管理员** | 公共网络下风险最高的一类 |
| 经代理 | 订阅域名暴露给**节点运营者** | 边际很小——它本就承载用户全部流量 |

> 措辞纪律：「两种选择都有代价，区别只在**代价给谁**」；**不写「走代理就没有隐私问题」**。

**② 档的失败语义**：用户在「走代理」模式下、隧道已断时点更新 → **自动回落直连并提示**「当前未连接，已改为直连更新（可能暴露订阅域名）」，**不得报「无法更新」**。

**`socks` 入站的双重职责（必需项，缺失即配置非法）**：①tun2socks 的中继入口（数据面）；②UI 自助更新的出口（应用服务层）。
> 未来做「精简配置」极易把它当冗余删除，**一次删除同时断掉数据面与订阅更新**，症状表现为"连不上"或"更新失败"，很难立刻归因。

**鉴权约束**：`FR-35` 要求本地入站默认开鉴权 ⇒ UI 走本地 SOCKS 必须携带凭据，**凭据从安全存储读取（D-16），禁止硬编码常量、禁止写入 UI 明文配置**（详见 §8.3）。

# 5. 路由与 DNS

## 5.0 防环路：三机制对照（三者不是同一件事，不可互相替代）

> 内核接管全设备流量后，**Xray 自己的出站连接也必须走物理网卡/绕开 tun**，否则「出站 → 落入 tun → 又回到 Xray」形成环路，方案直接跑不起来。这是**方案成立的一票，不是优化项**。

| 机制 | 作用对象 | 粒度 | 依赖的系统能力 | 失败后果 | OHOS 状态 |
|---|---|---|---|---|---|
| `blockedApplications=[自身包名]` | 该应用的 IP 流量是否进 tun | 应用（包名） | `VpnConfig`（建连期配置） | 未排除 → 出站被自己 tun 接住 → 环路 | 可用；**判定见 §3.4 gate-0a a2** |
| `protect(fd)` | **本应用创建的 socket** | 单 socket | `VpnConnection` 实例（扩展进程上下文） | 未 protect 的 socket 被 tun 接住 → 环路 | 可用；**跨进程范围 = `VD-25`/`P-27`** |
| `sockopt.mark` | 内核出站 socket | 单 socket（打标） | 系统策略路由按 mark 分流 | 打标无效 → 仍环路 | **未验证**（`VD-24`） |
| `sockopt.interface` | 内核出站 socket | 单 socket（绑网卡） | 绑定物理网卡权限 | 绑定被拒 → 回落 | **未验证**（`VD-24`） |

**判定规则**：三者**任一条可用即成立**（`VD-24` 是「三选一」，不是「mark/interface 必须可用」）。
**致命混淆点（显式警告，防实现期踩坑）**：
> `protect()` 保护的是**本应用主动创建的 socket**；`mark`/`interface` 解决的是**内核出站 socket** 的回落选路；`blockedApplications` 是**建连期按应用排除引流**。三者作用对象不同、**不可互相替代**；只做其一会导致 Xray 出站被自己的 tun 接住 → 环路。反过来的错误同样常见（照搬 Android 的 `protect()` 却因进程边界不同而失效）。

**时序约束（三步 API 序列，不是"create 之前"）**：
```
vpnExtension.createVpnConnection(ctx)  → 得到 VpnConnection 实例
connection.protect(tunnelSocketFd)     → 保护隧道 socket
connection.create(VpnConfig)           → 建 tun，返回 tun fd
```
硬序是「**protect 在 `create(VpnConfig)` 之前**」：tun 生效前完成 protect，隧道 socket 才不会被自己的 tun 捕获。
**实现保障（不靠人记）**：出站/隧道 socket 的创建必须经过统一工厂函数，工厂内完成上述三步顺序后才把 fd 交给协议层；**禁止裸 `net.Dial`、禁止业务层直接调用 VPN API**。

`【待验证】VD-24 Xray 出站 socket 能绕开 tun（blockedApplications / protect / sockopt.mark / sockopt.interface 四条至少一条在 HarmonyOS 可用）｜验证方式：真机起连后在 tun 计数器与物理网卡计数器上比对自身出站流量归属，四机制逐一对照｜归属：P-30（批次 B-02）｜失败后兜底：由 tun2socks 侧统一承接出站、内核只做协议，或限制路由捕获范围（放弃全局代理语义）`

## 5.1 分层路由：引擎层为主、系统层为辅（D-11）

### 5.1.0 平台硬约束：路由只能「建连时一次性下发」
VPN 路由**只能**通过 `create(VpnConfig).routes` 一次性下发，**没有** `addRoute`/`setRoute`/`updateConfig` 等动态接口。由此推出：

| 层 | 可变性 | 内容 | 改动代价 |
|---|---|---|---|
| **系统层（不可变）** | 建连后不可改 | `routes`（≤1024 条）、`addresses`、`mtu`、`isIPv6Accepted`、`trusted/blockedApplications` | **必须重建 VPN = 断连** |
| **内核层（可变）** | 可热改 | 域名/IP/端口/geosite/geoip/sniffing 等全部**分流决策** | 可不重建（按 D-33 热更或快速重启内核） |

**结论**：①**分流不能靠改路由表实现**，所有分流决策必须落在内核规则里，系统路由表只是一份**粗粒度接管范围**；②系统层只承担三件事：全量接管（`0.0.0.0/0` + `::/0`）、预置 LAN/内网绕过前缀表、排除自身（a2）；③用户可感知后果必须前置告知（见 §7 E20/E21）。

### 5.1.1 两层能力对照

| 层 | 手段 | 粒度 | 局限 |
|---|---|---|---|
| 系统层（`VpnConfig`） | `routes`（≤1024）、`trusted/blockedApplications`（**互斥**）、`dnsAddresses` | 粗（仅 IP 网段与应用级黑白名单） | 无域名粒度；条数受限；名单二选一；**建连后不可变** |
| 引擎层（Xray routing + sniffing） | 域名/IP/端口/协议嗅探/规则集 | 细（域名、geosite、正则、组合条件） | 全部流量必须先进 tun 才能判 |

**决策：`routes` 全量进 tun，分流由引擎层做。** 系统层只用于排除自身（a2）与少量粗粒度排除（内网/局域网）。
被否方案：用系统层 `routes` 实现「绕过大陆」——受 1024 条限制且大陆 CIDR 远超此数，会漏判；且无域名能力，无法处理 CDN/泛域名。

**分应用代理**：`trusted/blockedApplications` 只能表达「仅这些走 / 这些不走」，**两者互斥**、无混合能力 ⇒ 产品只能提供「全部应用 / 仅选中应用 / 排除选中应用」三档，**不承诺「按应用 + 按域名」组合策略**（引擎层拿不到发起进程）。
**容量上限（官方明文）**：API <23 最多 **64** 个包名，API ≥23 最多 **256** 个 ⇒ 名单按 **64/256 双档**设计（`deviceInfo.sdkApiVersion` 判定），**超限必须在 UI 拦截提示**，不能靠 `create()` 报错兜底。
**名单数据源自建（D-28）**：三方无法枚举已安装应用（`getInstalledBundleList` 属企业/MDM；`getBundleInfo` 等需 `GET_BUNDLE_INFO_PRIVILEGED`）⇒ 预置常见包名映射 + 搜索 + 手动输入 + 本地缓存；**接受「包名变更/应用分身/同名不同签名」导致静默失效**，仅给弱信号复核提示（§7 E17）。

## 5.2 规则组织方式

- 分层：**内置基础集**（私有网段、mDNS、回环）→ **用户规则**（最高优先）→ **订阅规则** → **默认策略**（全局/规则/直连）。
- 匹配顺序固定：`用户规则 → 订阅规则 → 内置集 → 默认策略`，**顺序不可由订阅内容改变**（防订阅注入流量劫持）。
- 规则来源安全：订阅只能改规则匹配，**不能新增出口节点**（出口仅来自用户显式导入的节点）。
- **默认策略必须 fail-closed**：未知域名走代理（"未知走直连"在大陆网络环境等价于默认泄漏）。
- 生效需**原子**：新规则加载失败 → 保留旧规则集并提示，不允许部分生效。

## 5.3 GeoIP / geosite 资源更新（D-13）

- 资源与内核版本解耦：独立版本号 + 校验和；**随包内置基线**（离线可用），运行时按需更新（更新出口见 §4.8 三档）。
- 流程：下载 → 校验（哈希/签名）→ **原子切换**（写新文件 + 切换引用，不原地覆盖）→ 加载失败则自动回滚旧资源。
- 回滚判据：加载异常 / 规则条目数为 0 / 启动自检失败 → 回滚并标记「资源异常」。
- 内置资源与运行时资源**共用同一套版本与校验机制**（避免版本不一致导致回滚判定混乱）。

## 5.4 DNS 方案（D-12）

- **关闭系统 resolver 依赖**：内核侧统一走内置 DNS 客户端（避免 musl/cgo resolver 与 FakeDNS 冲突）。
- `VpnConfig.dnsAddresses` 指向本地 DNS 端点，使被代理应用的查询进入我们的解析链路。
- 模式（用户可选）：`直连 DNS` / `加密 DNS（DoH/DoT）` / `FakeDNS + 远程解析`。
- **寻址方式三档（不并列，按风险排序）**：

| 档位 | 寻址 | 定位 |
|---|---|---|
| **主方案** | tun 网段内地址（如 `10.0.0.2:53`，应用在 tun fd 上应答） | 与官方语义一致；【待实测 E14-A】但**不称"候选"** |
| 备选 | `127.0.0.1:53` | 仅当 A 失败才测（回环监听、<1024 端口、resolver 是否认回环三重未知） |
| 对照组 | 外部 DNS（如 `223.5.5.5`） | 仅用于证明 A 是否生效；若只有它通过 → 平台不允许应用接管 DNS，降级为「纯 IP 路由 + 域名嗅探」 |

- **必须写死的约束**：`routes` 必须覆盖 DNS 地址所在网段，否则查询不进 tun，现象是「**域名全部解析失败但 IP 直连可用**」，极易误判为 DNS 配置不生效——**实测先查路由表**。
- **FakeDNS 与系统 DNS 链路共存风险**：伪 IP 可能被缓存导致「DNS 污染残留」⇒ ①VPN 断开时**清空 FakeDNS 映射**；②伪 IP 段避开常用内网段；③**FakeDNS 默认关闭**，作为高级选项（由 `VD-08`/P-09 决定是否默认开）。
- **DoH 失败降级**：加密 DNS 不可用 → 按用户设置回退直连 DNS 或直接失败提示，**不得静默回退**（静默回退会让用户以为加密生效，属安全问题）。

## 5.5 IPv6：恒接管 + 内核侧阻断（D-25）

默认 `isIPv6Accepted=true` + `addresses` 配 v6 + `routes` 覆盖 v6 + 内核侧 `block ::/0`（秒拒）⇒ 默认状态 v6 **既不泄漏也不可用**，应用回落 IPv4。

- **为什么不是「关掉 flag」**：`isIPv6Accepted` 文档默认 `false`，关掉意味着 v6 流量根本不进 tun（`isBlocking` 也无从阻断）→ 「v4 走代理 / v6 直连漏出」。**「接管 + 核心阻断」把隐私缺陷降级为功能未启用，是承诺质量的实质提升。**
- UI 文案：「IPv6 已接管并阻断（如需 v6 请在设置开启）」，而非「v6 不受保护」。
- **必须披露的体验代价**：`block ::/0` 对双栈探测/`Happy Eyeballs` 的影响需实测，用户可能感知为「某些站点打开变慢」——属主动披露项，不是隐藏项。
- 写错即泄漏的实现细节：`::/0` 必须写成 `gateway.address=''` + `hasGateway:false` + `isDefaultRoute:false`，否则 HarmonyOS **丢弃该路由**、v6 从物理网卡泄漏。

`【待验证】VD-18 IPv6 流量在「接管 + 内核 block ::/0」配置下不泄漏且不影响双栈探测可用性｜验证方式：对端 v6-only 探测 + tun 计数器 vs 物理网卡计数器比对 + 切换 Wi-Fi/蜂窝后重测（路由重建是最易丢 `isDefaultRoute:false` 的时刻）+ Happy Eyeballs 站点打开耗时对照｜归属：P-21（批次 B-04）｜失败后兜底：关闭 IPv6（`isIPv6Accepted=false`）并在 UI 明示「本次连接仅 IPv4」`

`【待验证】VD-08 FakeDNS 在 HarmonyOS DNS 链路下不产生污染残留（断开后可立即恢复解析）｜验证方式：FakeDNS 开启下单次连接→断开→立即访问域名，观察是否命中陈旧伪 IP｜归属：P-09（批次 B-04）｜失败后兜底：FakeDNS 默认关闭，仅在高级设置可开并加风险提示`

> 证据基线：`harmony-platform-constraints.md` v1.0 §4/§5/§6 + `harmony-permission-checklist.md` v0.1

# 6. 可观测性

## 6.1 日志分级与脱敏

| 级别 | 用途 | 默认开关 | 落盘 |
|---|---|---|---|
| ERROR | 内核崩溃、隧道建立失败、配置加载失败 | 常开 | 是（环形缓冲，保留最近 N 条） |
| WARN | 网络切换、重连、订阅刷新失败、长时任务被取消 | 常开 | 是 |
| INFO | 连接状态机迁移、节点切换、分流规则命中摘要 | 常开 | 是 |
| DEBUG | 规则匹配明细、DNS 查询链路 | **默认关**，用户可开 | 是（独立文件，容量上限） |
| TRACE | 单连接级时序 | 默认关，仅排障模式 | 否（内存环形） |

**脱敏红线（不可配置、不可绕过）**：订阅 URL 与其 token、节点 uuid/密码/Reality 私钥、SNI 之外的完整 URL 一律不落日志；日志中的节点标识只保留「节点名 + 哈希前缀」。理由：日志可能被用户导出分享，一旦含凭据即等同于泄漏配置。

- 通道：ArkTS 侧 `hilog`；Native 侧 `<hilog/log.h>`；**扩展进程内禁止使用 C6 列出的 API**（contact/geolocation/audio/camera/telephony），故扩展进程的诊断只能走 hilog + IPC 回传 UI 进程，不能借通知/音频等通道。
- 跨进程日志需 `requestId` 贯穿（UI 指令 → 内核 → 扩展进程），否则 A1 拓扑下的排障等于盲猜。

## 6.2 流量统计

- 口径定义（必须在文档里钉死，避免各处不同）：**上下行字节数按「内核出口 socket 的实际收发字节」计**，含协议封装开销、不含 tun 侧重传；分节点/分应用两维统计；时长统计以「连接状态机处于 Connected 的累计时间」为准。
- 与实况窗共用数据源：长时任务 `dataTransfer` 要求「首次进度更新 ≤10 分钟」，用同一份统计刷新实况窗进度 —— **一次采集两处消费**，不为保活造伪数据（第 3 章 L1 的落地前提）。
- 存储：日/周聚合落 RDB（`StoreConfig.encrypt=true`），明细只保留滚动窗口，防止无限增长。

## 6.3 崩溃与诊断

- Native 崩溃用 `faultLogger` 采集；Go 侧 `recover` + 看门狗；崩溃后由存活侧落盘「崩溃时间戳 + 配置指纹 + 最近 N 条内核日志」。
- **无符号崩溃栈等同不可运维** → 发布包保留符号表（不上架包内，按版本归档），诊断导出时按版本号映射。
- 诊断导出：用户可一键导出（脱敏后）诊断包，供反馈；这是「崩溃可观测」在无后台服务时的最低成本实现。

# 7. 错误处理与降级矩阵

| # | 场景 | 触发 | 用户可见行为 | 系统侧动作 | 兜底 |
|---|---|---|---|---|---|
| E1 | 首次授权被拒 | 系统弹窗拒绝 | 说明页解释为何需要 VPN + 手动重试入口 | 状态机停 `Idle`，不做自动重试 | 引导至设置 |
| E2 | 已被其它 VPN 占用 | `2203002` | 「同时仅允许一个 VPN，请先断开其它 VPN 应用」+ 重试 | 回滚 `Idle`，不残留上下文 | 预检 + 引导跳转 |
| E3 | GUEST 用户 | `2203001` | 「当前系统用户类型不支持 VPN」 | 不重试（硬约束） | 仅提示 |
| E4 | 其它启动失败码 | `2203004` 等（**待 K1 核实出处**） | 通用失败提示 + 诊断入口 | 落盘错误码与上下文 | 诊断导出 |
| E5 | 用户手动杀掉应用 | 用户划掉任务卡片 | **VPN 必然断开**（C3：调用方进程退出系统即停 VPN） | 记录「非正常断开」标记，下次启动首页强提示「上次连接已中断，是否重连」 | 无（平台约束，只能补偿） |

| E7 | 内核崩溃 | Go panic / SIGSEGV | 「内核异常，正在恢复」→ 恢复失败则「需重启应用」 | 存活侧重启内核并 `reload(last-good-config)`，带次数上限 | 整进程重启 + 诊断落盘 |

| E9 | 长时任务被取消 | `continuousTaskCancel` / 用户删通知 | 「后台运行已停止，退出应用将断开连接」 | 停止保活分支，状态转「受限运行」 | 提示用户重新开启 |
| E10 | 订阅拉取失败 | 网络/服务端/格式错误 | 「订阅更新失败，继续使用上次配置」 | 保留 last-good 配置，不覆盖 | 标记订阅「过期」并提示 |
| E11 | 订阅格式不合法 | 解析失败 | 「订阅格式不支持」+ 原始响应脱敏预览 | 拒绝导入，不改动现有配置 | 提供手动粘贴导入 |
| E12 | 配置校验失败（内核拒绝启动） | 内核启动报错 | 「配置无效，已回滚到上次可用配置」 | 原子回滚 + 落盘失败原因 | 进入安全模式（仅直连） |

| E14 | 存储空间不足 | 写盘失败 | 「存储空间不足，日志与统计已暂停」 | 停 DEBUG 日志与统计聚合 | 保留 ERROR/WARN |
| E15 | 公开上架被拒（分发侧） | 应用市场审核驳回 | 不涉及用户侧 | 见 §9.3 路径切换 | 走内部/自用分发 |

| E16 | IPv6 泄漏（路由被丢弃） | `::/0` 未按 `gateway.address=''`+`hasGateway:false`+`isDefaultRoute:false` 配置 | 界面不提示（静默）；诊断页标红「IPv6 未接管」 | 发布前检查单阻断（RG-02） | 关闭 IPv6 + 明示仅 IPv4 |
| E17 | 分应用名单失效 | 包名变更 / 应用分身 / 同名不同签名 | 「名单项可能已失效，建议复核」 | 弱信号检测（读取该包名失败） | 用户手改，不承诺自动修复 |
| E18 | 显示已连接但隧道已死（静默失败） | 一阶 tun fd 写失败 / 二阶心跳超时 | 「连接异常，正在恢复」→ 恢复失败提示重连 | D-32 健康判定统一置位并上报 | 自动重建连接 |
| E19 | UI 复活后状态不一致 | 主进程被回收后重启 | 短暂显示「正在同步状态」，随后以真实状态渲染 | D-31 对账（禁止沿用本地缓存） | 以内核状态为准 |
| E20 | 改「接管网段」类设置 | 系统层字段变更（`routes`/`addresses`/`mtu`/`isIPv6Accepted`/应用名单） | 二次确认：「将断开连接并重建」 | 重建 VPN | 取消则改动不生效 |
| E21 | 改「分流规则」类设置 | 内核层字段变更 | 提示「本次改动无需断开」 | 热更规则 / 快速重启内核（D-33） | 失败回滚旧规则并提示 |

# 8. 安全设计

## 8.1 敏感数据落盘

| 数据类型 | 方案 | 依据/约束 |
|---|---|---|
| 节点凭据（uuid、密码、Reality 私钥、订阅 token） | `@ohos.security.asset`（ASSET） | AES256-GCM 在 TEE 内完成；**单条 ≤1KB**；以「业务身份 + 别名」唯一索引；卸载会清除（`IS_PERSISTENT` 决定是否保留） |
| 节点库/订阅/路由规则批量数据 | RDB + `StoreConfig.encrypt = true` | 密文存储；**加密属性创建时确定、不可变更** → 一旦启用无法改回明文，需自建导出 |
| 数据库加密密钥 | `@ohos.security.huks` | 明文密钥不出安全环境；需设计密钥别名与用途 |
| UI 偏好（主题/上次节点索引） | `preferences` | **禁止放任何敏感数据**（非安全存储） |

- 约束落地：ASSET ≤1KB → 长文本（如完整订阅原文）必须落 RDB 加密库，ASSET 只存「索引 + 短凭据」。
- 换机迁移 = 重新导入订阅（ASSET 与应用生命周期绑定），需在需求侧定义为可验收用例。

## 8.2 内存中的密钥处理

- 内核侧（Go）持有的私钥只在启动配置构建时传入，**不做全局缓存、不写 debug 日志**；配置对象在隧道建立后立即释放引用，由内核自身持有会话密钥。
- 禁止把凭据拼进任何「诊断导出」内容；导出前统一走脱敏过滤器（白名单式，非黑名单式）。
- ArkTS 侧不长期持有明文凭据：从 ASSET 取出 → 立即用于构建内核配置 → 丢弃引用。

## 8.3 调试接口隔离

- 内核若暴露本地控制/统计接口（如本地 HTTP/gRPC 管理口），**必须**绑定 `127.0.0.1` + 随机端口 + 一次性 token，且**仅在 DEBUG 构建开启**；发布构建关闭。
- 代理入站（若为形态 B）必须默认只监听回环，禁止 `0.0.0.0` 无认证监听——这既是安全底线也是上架审核红线。
- `VpnExtensionAbility` 内**禁止引用** `@ohos.contact` / `geolocation` / `multimedia.audio` / `camera` / `telephony.call|sim|sms`：违者进程异常退出。该清单是**实现期必踩点**，在架构层即约束「引擎侧不得依赖这些能力」。
- 权限最小化：仅声明 `ohos.permission.INTERNET`、`GET_NETWORK_INFO`、`KEEP_BACKGROUND_RUNNING`（按需）；`KEEP_BACKGROUND_RUNNING_SYSTEM` 仅在确有需要时申请，并在隐私政策逐项对齐（上架审核会复核）。
- 隐私：不采集设备标识用于画像；诊断数据默认本地、用户手动导出——这同时降低合规成本。

# 9. 版本与灰度

## 9.1 内核版本与 App 版本解耦

- 内核以 so 形式随包分发（平台无独立可执行/子进程，见 §3.1），**内核版本必须作为独立版本号随 App 记录**（App 版本 → 内核 commit/版本 的映射表进发布档案）。
- 配置 schema 与内核版本绑定：内核升级可能改动配置字段 → 需「配置 schema 版本号 + 迁移器」，迁移失败一律回滚 last-good 并保留旧配置。
- 灰度手段（无自有服务端时）：按 App 内灰度开关 / 渠道包 / 分批放量；内核行为变更必须可运行时回退（双内核共存不现实，改为**快速回滚版本**）。

## 9.2 升级与回滚

- 升级路径：下载 → 校验（签名/哈希）→ 原子替换 → 启动自检（起内核、加载配置、跑一次自检连通性）→ 失败自动回滚上一可用版本。
- 回滚判据（可机检）：自检失败、连续 N 次崩溃、或订阅/配置迁移失败。
- so 构建可复现性：**预构建 so 必须由 OpenHarmony NDK 同源工具链编译，依赖库同样要求**；构建脚本、NDK 版本、flags 必须随版本归档，否则无法复现、无法审计（也是 MPL-2.0 源码可得性承诺的一部分）。

## 9.3 分发与合规三条路径（含审核不通过时的产品路径）

| 路径 | 前置 | 周期 | 代价 | 审核不通过时的产品路径 |
|---|---|---|---|---|
| P-a 调试自用 | 个人实名 + 调试证书/Profile + 真机 UDID | ~0.5~1 工作日 | 上限 **100 台设备**，不可面向公众 | 不涉及审核；仅限自用与团队内测 |
| P-b 企业内部/小范围分发 | **独立未实名华为账号** + 企业实名 + 企业内部应用分发资格 + 组织内部发布证书（每账号 1 个） | ~3~8 工作日 | 仅组织内成员可用；需维护独立账号体系 | 若资格被拒 → 退回 P-a，产品仍可验证但无法规模化 |
| P-c 公开上架应用市场 | 企业主体 + **IP-VPN 类增值电信业务经营许可证**（跨省注册资本 1000 万 / 省内 100 万，法定审查 60 日）+ 软著/备案 | 1~4 个月 | 资金与主体门槛最高 | **①类目资质缺失被拒** → 走 P-b + 保留 P-c 补证后重提；**②被判定为「跨境代理/规避网络管理」类工具而禁售** → 形态 A 的商业化路径不成立，产品定位改为「企业内部网络接入工具」走 P-b，或退形态 B 并明示能力损失（无全局透明代理/无分应用路由/仅浏览器与支持代理的 App 可用） |

- 关键结论：**形态 A 的技术成立 ≠ 商业化成立**。技术侧零审批，商业侧的闸门在存量资质与类目判定；因此 §9.3 的三条路径必须在需求阶段就由产品侧选定，不能留到发布前。
- 合规标注：Xray-core 为 **MPL-2.0**（文件级 copyleft）。分发义务落到：随包提供 LICENSES/NOTICE、被修改的源文件可得性承诺（源码获取途径）、构建脚本可复现。此项为**确定性合规要求**，非待验证项，落地检查见发布前检查单。
- **政策不确定项**：类目资质最终以审核意见为准 → 归属责任角色（policy），须在提审前以工单索取书面答复并留档；本设计给的是「不通过时走哪条路径」，不是「建议咨询」。

【待验证】VD-20 Xray 的 SOCKS 入站支持 UDP ASSOCIATE，tun2socks 的 UDP 流量（QUIC/DNS）可经其转发｜验证方式：跑 HTTP/3 站点 + DNS over UDP + VoIP，观察是否回落/失败｜归属：P-28（批次 B-04）｜失败后兜底：明确能力边界 + QUIC 回落引导（属功能缺陷，不属性能问题）
【待验证】VD-21 扩展进程内存/堆上限足以承载 Xray 内核 + gvisor 栈｜验证方式：扩展进程内跑内核 + tun2socks，测 RSS/堆峰值 + **8h 长跑堆增长斜率**，基线用「同进程 ArkTS 空载」｜归属：P-24（批次 B-02）｜失败后兜底：锁 A3（内核驻主进程）
【待验证】VD-22 主进程退出/被杀后是否存在孤儿隧道｜验证方式：三种死亡方式分开测（用户划掉 / `hdc shell kill` 主进程 / 扩展进程自身被回收），每次观察扩展进程存活、tun 是否消失、状态栏图标、**对外出口 IP 是否变化**；本机 `curl` 成功不构成证据｜归属：P-25（批次 B-07）｜失败后兜底：fail-closed 看门狗（心跳 + 文件锁可获取 + 观察窗口，三条件同时成立才 `destroy()`）
【待验证】VD-23 同应用跨进程 loopback 可达（A3 默认路径必测）｜验证方式：扩展进程 tun2socks ↔ 主进程 Xray 的 SOCKS 链路双向数据通 + 并发压测｜归属：P-29（批次 B-04）｜失败后兜底：A3 不成立 → 只能 A1（若 A1 亦不成立则停线）
【待验证】VD-24 Xray 出站可绕开 tun（`blockedApplications` / `protect` / `sockopt.mark` / `sockopt.interface` 四选一）｜验证方式：起连后比对 tun 计数器与物理网卡计数器的自身出站流量归属，四机制逐一对照｜归属：P-30（批次 B-02）｜失败后兜底：由 tun2socks 侧统一承接出站，或限制路由捕获范围（放弃全局代理语义）
【待验证】VD-25 `protect()` 的作用范围是否跨进程｜验证方式：0a `VpnConnection` 实例/句柄能否在主进程获得（或经 IPC 传递）→ 0b 主进程建 socket 后 protect，看流量是否仍进 tun，与扩展进程内同款对照 → 0c 退 `mark`/`interface`/限制路由｜归属：P-27（批次 B-02）｜失败后兜底：A3 出局、A1 强制（并连带把 VD-19/VD-21/VD-22 从"选型权衡"升级为"交付门槛"）
