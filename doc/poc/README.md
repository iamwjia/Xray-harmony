## 3. 方法论 A · 受控失败对照（negative control）

> 来源：架构侧起草、team-leader 审订。**原样采用，六条不合并。**

1. **凡具备明确二值判据的 PoC，必须包含至少一个「已知应当失败」的受控对照**，用于证明该实验的通过判据确实能分辨失败（例：定路段 A 不配 `blockedApplications`、段 B 不调 `protect`、段 C 不打 mark）。
2. **受控失败若「通过」了 ⇒ 判据本身失效**：该实验**此前所有「通过」结论一并作废**（不是"这条对照有问题"，而是**前面的结论一起不成立**）——先修正判据，再重跑全部用例。
3. **受控失败必须与正式实验在同一台设备、同一次会话内完成**：跨设备/跨版本/跨构建做对照，差异会被环境噪声吞掉，等于没做。
4. **适用范围**：仅限**有明确二值判据**的实验；纯探测类（如 `P-18` 应用枚举能力）没有"通过/失败"概念，**不强求套用**，避免为凑形式编造假对照。
5. **记录方式**：受控对照与正式用例**并列记入记录模板**（同一复现率口径），不得只在正文里口头说明。
6. **反向配置应尽量与正式配置只差一个变量**：差两处以上时，"对照失败"无法归因到具体机制，规则就退化成仪式。

### 3.1 现成实例（可查、可抄）

| 实例 | 出自 | 是什么 | 判读 |
|---|---|---|---|
| **A / B / C / D 四组反向配置** | [PC1](./PC1-topology-gate.md) **附录 A** | A：不配 `blockedApplications`；B：不调 `protect`；C：不打 mark；D：先销毁扩展进程再取对象 | 反向"通过"⇒ 该实验判据失效，此前通过作废 |

| **用 main 分支编译（PC2）** | [PC2](./PC2-build-chain.md) §0.1、§7 | 故意取 `libXray` main：`go.mod` 要求 go 1.27.1 | 预期构建**报 `module requires go >= 1.27.1`**。若竟然编过 ⇒ 说明钉版规则失效/工具链已漂移，须先复查 |

## 4. 方法论 B · 静默 / 报错二分（防假阴性）

> 来源：平台侧起草，team-leader 认可。**与 §3 并列，是同一套方法的两半，不分开放。**

**能报错的是「版位不足」，不报错只静默不同的是「语义不同」**——后者最容易把"测不到"判成"平台不支持"。
可推广到所有平台能力探测：**报错说明你撞到了边界，静默说明你根本没撞到**。

**两条方法论是一枚硬币的两面**：

- **受控失败对照防假阳性**：构造"必然失败"的条件，若它仍「通过」⇒ 判据失效（**判据自检**）；
- **静默/报错二分防假阴性**：静默通过时无法区分"生效了"与"没撞到边界"，必须补一条**能撞到边界的对照**（例：用超上限的分应用名单触发 `2200001`），若连这个都不报错，说明测的根本不是新逻辑（**边界自检**）。

> **合起来是一条纪律：每个判据都必须配套一个「它应该失败」的对照；没有对照的「通过」只是「没观察到失败」。**

**本手册据此要求的记录扩展**：每个实验记录里，除判定本身必须多写两格——

| 格 | 判据自检（方法论 A） | 边界自检（方法论 B） |
|---|---|---|
| 写什么 | 反向配置做了什么 + 结果（预期失败 / 竟然通过） | 撞了哪条边界输入（见 §5）+ 是否如预期报错 |
| 异常判读 | 反向也通过 ⇒ **该实验全部通过作废** | 连边界输入都不报错 ⇒ **测的不是新逻辑**，先证明跑的是新代码 |

## 5. 撞边界输入清单（方法论 B 的可执行落地）

> 规则：**每包至少一条**，与正式用例同设备同会话执行；**期望报错却没报错 ⇒ 该包"静默通过"不可信**。
> 用途不是"制造麻烦"，而是证明：**你测的那条路径真的有边界，且系统在边界上会说话。**

| 包 | 撞边界输入 | 期望反应（作为"如实报错"的判据） | 若不报错意味着什么 |
|---|---|---|---|
| **PC1**（定路） | ① 分应用名单**超上限**（API 12~22 配 >64、API 23+ 配 >256）<br>② `trustedApplications` 与 `blockedApplications` **同时配**（官方称互斥） | ① 期望 `create()` 报 `2200001`（或明确拒绝）<br>② 期望报错，或明确"其中一个被覆盖" | ① **静默截断** ⇒ 名单上限测不出，必须改用「第 N+1 个应用流量是否真走 VPN」判定（PC4 §5 已提示）<br>② 既不报错也不覆盖 ⇒ "互斥"语义在本机不成立，须重判 a2/a1 的作用模型 |
| **PC2**（构建链） | ① 故意取 `libXray` **main** 编译<br>② `dlsym` 一个**不存在的符号**<br>③ 向 `CGoInvoke` 传**不合规 JSON**（缺 `apiVersion`） | ① 报 `module requires go >= 1.27.1`<br>② 返回 NULL + `dlerror` 有内容<br>③ 返回 `success:false` + `error` 字段（**不得崩溃**） | ① 竟然编过 ⇒ 钉版/工具链已漂移<br>② `dlsym` 拿得到 ⇒ 导出面失控（攻击面 + 升级不可控）<br>③ 崩溃 ⇒ 入参校验缺失，`J-01` ② 结论不可信 |
| **PC3**（tun 链） | ① `VpnConfig` **缺必填字段**（如无 `addresses`/`routes`）<br>② `routes` **超 1024 条**<br>③ 配置里写**不存在的 `protocol` 值**<br>④ SOCKS 入站**错误鉴权 token**<br>⑤ 构造**超 MTU 包** | ① `create()` 报参数错误<br>② 报错或明确拒绝<br>③ 内核**启动失败**（不得静默回落直连）<br>④ 拒绝连接（不得放行）<br>⑤ 丢弃该包并计数（不得崩溃/卡死） | ① 静默接受 ⇒ 参数校验形同虚设，后续"配置生效"结论不可信<br>③ 静默直连 ⇒ **最危险**：看起来通了其实没代理<br>④ 错误 token 也放行 ⇒ 本地入站端口等于对同机任意应用开放（`FR-35` 失效） |
| **PC4**（观测包） | 在**低档位设备**上调用高版位 API（如 API 12 设备调 `generateVpnId`） | 报 `is not a function` / `undefined` / 参数错误 | 不报错 ⇒ 该档位判定用的是"新逻辑"，档位矩阵结论作废 |

> 记录要求：把"输入 → 期望 → 实际 → 是否一致"填进 §8.1 的「边界触发（边界自检）」格；**一致才算边界自检通过**。
