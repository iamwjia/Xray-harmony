# PC16 — DNS 走隧道（分流正确性的前置条件）

日期：2026-11-22
范围：`service/KernelConfigBuilder.ets`（`buildDns`、`dnsRule`）、`tests/config-builder.test.js`

## 1. 问题

分流规则大量基于**域名**（`geosite:cn`、用户自定义 `domain:`）。如果解析发生在设备上：

- 「哪些域名被查询」本身就泄露了你要访问什么；
- 即使后续流量走了代理，DNS 已经先告诉了本地网络。

所以 **DNS 查询必须和流量走同一条路**。

## 2. 实现

```
"dns": { "tag": "dns-in", "queryStrategy": "UseIP", "servers": ["1.1.1.1", "223.5.5.5"] }
routing.rules 第一条：{ "type":"field", "network":"tcp,udp", "port":"53", "outboundTag":"proxy" }
```

三个刻意的决定：

1. **53 规则排在最前**：否则会被 `geosite:cn` 之类的规则先命中，变成"国内域名的 DNS 走直连"——那正是要避免的泄露。
2. **`queryStrategy: UseIP`**：避免同一域名同时拿回 IPv6 导致后续走不通（当前 IPv6 策略是接管并阻断）。
3. **两个解析器（1.1.1.1 + 223.5.5.5）**：只给外国解析器会让国内域名变慢，只给国内解析器又会对被污染域名返回坏结果。

**直连模式不生成 `dns` 段**：那个模式下用户就是要本机直连，擅自改解析路径是多管闲事。

## 3. 语义变更（对 GLOBAL 模式）

全局模式以前**不生成 routing 段**，结果"全部流量走代理"只管流量、不管查询。现在固定带一条 `53 → proxy`。
测试里有一条断言从「GLOBAL 不生成 routing 段」改成「GLOBAL 只带一条 DNS 规则且走代理」——这不是放宽，是把语义说清楚。

## 4. 实测

```
KernelService.start bytes=984
KernelService.start confirmed running=true
```

即：含 `dns` 段与 `53 → proxy` 规则的配置被内核**接受并成功启动**。（这次连接用的是不可达的测试节点，只验证"配置能被内核吃下"，不代表能上网。）

## 5. 边界（必须说清）

- 当前连接路径是 **socks 入站**：真正的解析发生在使用该 socks 的客户端里，本应用不本地解析，所以**这条 DNS 配置现在不产生实际流量效果**；
- 它真正开始起作用是在 **tun2socks 转发接线**之后——那时设备侧的 DNS 查询会进内核，必须由这条规则兜住；
- 也就是说：**这不是"已修复泄露"，而是"为转发路径准备好、并已被内核接受的配置"**。等转发接线完成，需要用真实域名验证 `tcpdump` 级别的证据。
