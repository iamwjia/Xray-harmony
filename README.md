# xray-harmony

> HarmonyOS NEXT 上的 Xray 代理客户端 —— 基于开源 Xray-core，目标是把「能用」做成「普通人能用」。

**当前状态：文档阶段已完成，PoC 实验尚未开始。仓库内没有实现代码。**

---

## 1. 这个项目要做什么

在 HarmonyOS NEXT 上做一个系统级代理客户端（类似 Android 上的 v2rayNG / NekoBox），内核复用 [XTLS/Xray-core](https://github.com/XTLS/Xray-core)。

已经有一个先行者：[`popsiclelmlm/Hey`](https://github.com/popsiclelmlm/Hey)（Xray 官方 README 收录的 HarmonyOS 客户端）证明了**技术可行**——它把 Xray 编译成 `.so`、用 NAPI 同进程加载、通过 `VpnExtensionAbility` 取 tun fd、再用 tun2socks 中继到本地 SOCKS。

但它**没有证明「产品可用」**：只发源码无 release、单人维护、不内置任何订阅源与规则集，主动放弃大众用户。

**所以本项目的空间不在"技术首创"，而在"产品完整度"**：订阅导入、节点管理、分流与 DNS 的完整性、诊断与恢复体验，以及合规的分发路径。

## 3. 最重要的一件事：可行性押在 `J-01` 一个假设上

```
J-01 = Xray 内核以 so 同进程加载（P-02→P-03→P-04）
     + 经 tun2socks 路径跑通 tun 数据面（P-01 × P-20）
     + v6 最小数据面用例
```

- **`J-01` 不通过 ⇒ 产品在当前平台不成立，不是"降级交付"。**
- **没有兜底**：手机端三方应用**无法创建独立子进程**（`16000061` / `801` / `NCP_ERR_NOT_SUPPORTED`），"内核独立进程"这条路不存在；备选形态（本地代理端口）已排入 V1，MVP 内无替代。
- 因此正确顺序是 **先证伪、再补全设计**，而不是先完成设计再验证。投入 5~6.5 周即可判定产品是否成立。

## 4. 已确认的平台硬约束（都有一手证据）

| 约束 | 影响 |
|---|---|
| tun 能力**不需要华为审批**：`VpnExtensionAbility` 对三方开放，仅需 `ohos.permission.INTERNET`（normal 级），首次启用是**用户授权弹窗** | 真正的门槛在**分发侧**，不在技术准入 |
| 系统**同时只允许一个 VPN**（错误码 `2203002`） | 必须做冲突检测与用户可见处置 |
| 三方应用**无法开机自启** | 「开机自动连接」不可实现，改为卡片/快捷方式一键启动 |
| **进程退出即停 VPN** | 「退出后继续代理」不成立 ⇒ **无进程级 kill switch**，已如实披露 |
| 手机端**不能起子进程**；`VpnExtensionAbility` 是独立扩展进程 | 内核只能 so 同进程加载；UI↔扩展进程有隔离，但**内核↔tun2socks 无隔离** |
| `proxy/tun` 在 `GOOS=openharmony` 下**编译为 stub** | 「Xray 直连 tun」需自研实现并承担 MPL 开源义务 ⇒ **走 tun2socks 是合规与工程双最优** |
| 系统只建虚拟网卡 + 下发路由/DNS | 隧道协议、tun fd 读写、socket protect **全部要自己实现** |

## 5. 技术路线（当前默认，待实测校正）

```
┌─ UI 层（ArkTS / ArkUI）────────────────────────────┐
│  订阅 · 节点 · 分流 · 诊断 · 恢复                  │
├─ 应用服务层 ───────────────────────────────────────┤
│  配置域模型 / 订阅解析 / 状态机 / 安全存储(HUKS)    │
├─ 核心引擎层 ───────────────────────────────────────┤
│  Xray-core（Go → .so，NAPI 同进程加载）             │
│  cgo 契约极窄：CGoInvoke(json)->json + CGoFree      │
├─ 平台适配层 ───────────────────────────────────────┤
│  VpnExtensionAbility · tun fd · 长时任务 · 通知     │
└────────────────────────────────────────────────────┘

数据面：tun fd → tun2socks(gvisor) → 127.0.0.1:<socks> → Xray 出站
```

**两个待定项**（由 PoC 决定）：
- **拓扑**：内核驻主进程（A3，先验默认）还是与 tun2socks 同驻扩展进程（A1，假设更少但耦合更紧）；
- **防环手段**：`blockedApplications` / `protect(fd)` / `mark` / `interface` 四选一。

**构建链**：Go fork `star4277/ohos-go v1.26.5-beta1` + `GOOS=openharmony` + `-ftls-model=global-dynamic`；`libXray` 必须钉 `v26.7.28`（main 已要求 go 1.27.1，现役 fork 编不了）。

## 6. 分发形态决定工期，不是审批决定

| 形态 | 资质前置 | 最短工期由什么决定 | 量级 |
|---|---|---|---|
| 自用 / 调试安装（≤100 台） | **无** | PoC 结论 | 5~6.5 周 |
| 内测 / 企业内部分发 | 企业实名 + 内部发布证书 | 与 PoC 并行 | 资质约 3~8 工作日 |
| **公开发行（AppGallery）** | **IP-VPN 类《增值电信业务经营许可证》** | 审批（法定 60 日内，社区实测 20~40 工作日）+ 企业主体、注册资本（省内 100 万 / 跨省 1000 万） | **月级，且类目可上架性存疑** |

> 早期文档曾写「最短工期由审批决定，不由开发量决定」——该结论基于已推翻的前提（误以为 tun 能力需华为资质审批），已更正并留痕。
